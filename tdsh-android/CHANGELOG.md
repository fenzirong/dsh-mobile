# 更新日志

本项目是 [DeepSeek Harness](https://github.com/deepseek-ai) 的**非官方**安卓封装。
版本号对应 APK 的 `versionName`，`versionCode` 每次递增 —— 同签名，可直接覆盖安装，
不会清空手机上的容器、API Key 与白名单。

## v0.4.21-fz1

（`versionCode 72 → 73`。**包名改为 `com.dsh.tdsh`**，项目迁入 `dsh-mobile` 仓库。）

### 为什么改

项目从 `Tdsh-DSH-Mobile-Android-NO-ROOT`（即将转为私密）迁到 `dsh-mobile`，
同时换一个干净的应用身份：`com.dshmobile.probe` → **`com.dsh.tdsh`**。

### ⚠️ 这是一次"换应用"，不是普通升级

| 项 | 影响 |
| --- | --- |
| 安装 | 新包名是**另一个应用**，可以和旧版并存；旧版不会被覆盖 |
| 数据 | **旧版的容器（约 150MB）、API Key、白名单、会话都不会跟过来** —— 新装是全新环境 |
| 签名 | 仍用同一把发布密钥；同包名的后续版本照旧可覆盖安装 |
| 权限 | `WRITE_SECURE_SETTINGS` 等一次性授权要**对新包名重新做一次**（`pm grant com.dsh.tdsh …`） |

想保留旧环境的话：先别卸载旧版，等新版把容器装好、确认可用之后再删。

### 怎么改的（可重复）

包名散落在 100+ 处（Java `package`/`import`、AIDL 的 `package` 声明与目录、
`AndroidManifest` 的组件名、`build.gradle` 的 `namespace`/`applicationId`、
`AGENTS.md` 里给 agent 看的 `pm grant` 命令、docs 里的 `run-as` 示例…），手改必漏。
所以做成脚本：

```bash
./tools/rename-package.sh com.dsh.tdsh com.example.newid
```

它会移动 Java/AIDL 目录、改写所有被 git 跟踪的文本文件、最后**自检残留**（有残留就报错退出）。
本次已用它把 88 个文件改完，并修掉了脚本第一版因文件名含中文而漏改的两处文档。

### 顺带

- `tools/rename-package.sh` 里的遍历改成 `git ls-files -z` + `read -d ''`，
  文件名含空格/中文也不会漏（第一版就是在这里漏了两个文档）。

## v0.4.20-fz1

（`versionCode 71 → 72`。按工作区里那个「合并 Termux」项目与 TAWC/dsh-go 的做法，
接上 **Termux 路线**：bionic 原生 node 直接跑 dsh。用户态未安装时安静回落 PRoot。）

### 参考项目给了什么，以及哪一步不能照抄

工作区 `dsh-mobile`（合并 Termux 版）已经把这条链路走通了，可直接借鉴：

| 借鉴点 | 说明 |
| --- | --- |
| 内置 bootstrap | 官方 `bootstrap-aarch64.zip`（30.7 MB）编进 `libtermux-bootstrap.so`，首次启动离线解压 |
| 装包前改写 | apt 的 `DPkg::Pre-Invoke` 钩子 → `dpkg-deb -R` 解包 → 改名/替换 → `dpkg-deb -b -Zgzip -z1` 重打包 |
| 重打包用 gzip -1 | 实测 48 MB 的 nodejs 包：`xz -6` **45.8 s** vs `gzip -1` **1.3 s**（35 倍） |
| 启停 | 后台跑脚本写阶段码，App 每 800 ms 轮询 token URL；后端已在跑就复用 |

**但它的关键技巧我们不能用**：它把包名定成 `com.dshapp`（**10 字节**），
与 `com.termux`（10 字节）等长，于是可以对 bootstrap 与每个 .deb 做**等长字节替换**。
本 App 的包名是 `com.dsh.tdsh`（**18 字节**），一变长就会破坏 ELF 的
`DT_RUNPATH` 与 bash 的编译期路径（`.rodata` 偏移）。

### 我们的接法：一个字节都不补丁，用 tawcroot 把前缀绑过来

```
tawcroot -r <空根> \
  -b files/probe/termux/usr : /data/data/com.termux/files/usr \
  -b files/probe/termux/home : /root \
  -b /system -b /dev -b /proc -b /sys -b /sdcard … \
  -- /bin/sh -c 'cd /sdcard/dsh && exec $PREFIX/bin/node …/dsh/lib/bin.js --profile web …'
```

于是 Termux 二进制里那些硬编码路径**天然全部指对地方**，连 shebang 都不用改；
顺带还解决了原生模式下 `link(2)` 被 SELinux 拒绝的问题
（dsh 的原子写与 pnpm 都依赖硬链接，tawcroot 自带模拟）。

代价：仍会经过 tawcroot 的 seccomp（只在命中前缀绑定的路径上，且是**进程内**处理，
比 ptrace 便宜一个量级）；单进程 → 与 tawcroot 同样的"没有隔离"取舍。

### 这一版落了什么

| 组件 | 状态 |
| --- | --- |
| `Env.RT_TERMUX` / `termuxCommand()`（tawcroot + 前缀绑定 + bionic node） | ✅ |
| `Env.termuxInstalled()`（只检查 `termux/usr/bin/node` 与 dsh 入口） | ✅ |
| `TermuxGate` 准入闸门（node/bash/dsh + 硬链接/符号链接/exec//proc//sdcard/pnpm） | ✅ |
| 设置项「Termux 原生运行时（实验）」+ 状态显示 | ✅ 默认关 |
| **用户态安装器**（下载 Termux 包并解包） | ⬜ 未做，见下 |

**为什么没把 30MB 用户态塞进 APK**：那是第三方 arm64 二进制，而我这边没有
arm64 真机可跑，无法验证。按本项目一贯的规矩（没验证的东西不随包发），
这一版只落"骨架 + 闸门 + 文档"，用户态由 `tools/termux/README.md` 里的手工路径验一次，
再决定是否做成"首次启动自动下载安装"。

### 怎么验

1. 按 `tools/termux/README.md` 把 `usr/` 放进 `files/probe/termux/`；
2. 设置 → 打开「Termux 原生运行时（实验）」→ 重启 App；
3. `report.txt` 会出现二者之一：
   - `· ✅ 运行方式：Termux 原生（bionic node，无 glibc/无 rootfs 翻译）`
   - `· ⚠️ Termux 原生运行时不可用（GATE_FAIL_xxx）→ 本次改用 PRoot`
4. 无论哪条，**功能都不受影响**（闸门不过就回落 PRoot）；
5. 插件市场回归：装一个纯 JS 插件确认能装能生效。

详见 `docs/termux-route.md`（含三条路线的代价对比与后续自动化计划）。

## v0.4.19-fz1

（`versionCode 70 → 71`。接上 **tawcroot** 运行时：把"每次 stat 都 ptrace 停一次"换成进程内 seccomp 模拟。
默认关闭，开了也要先过自检 —— **插件市场不受影响**是硬约束。）

### 为什么是 tawcroot

用户的真机 V8 profile 已经把结论钉死：dsh 冷启动 59 秒里 **86%** 是
`fstat/internalModuleStat/lstat/realpath`，`voluntary_ctxt_switches` 14 万次 ——
也就是 **PRoot 每次路径翻译都要停一次进程**。所以优化 JS 是白费力气。

[tawcroot](https://github.com/wmww/tawc) 是从零写的 fake chroot：**seccomp `RET_TRAP` +
进程内 `SIGSYS` 处理**（gVisor 的 "systrap" 思路），路径翻译、fake root、硬链接模拟
全在同一进程里完成，**没有 tracer、没有每次系统调用的上下文切换**。上游实测启动约快 3 倍。

### 与 PRoot 的差异（每一条都可能在"插件市场"上表现出来）

| 项 | PRoot | tawcroot | 我们的处理 |
| --- | --- | --- | --- |
| 调用形式 | `proot -r … -0 -w … --link2symlink --kill-on-exit -b …` | `tawcroot [-s] -r ROOTFS [-b SRC:DST[:ro]]… -- CMD` | 新增 `Env.tawcrootCommand()` 单独生成 |
| 假 root | `-0` | 总是伪装 uid 0 | 去掉 `-0` |
| 硬链接 | `--link2symlink`（符号链接冒充） | **原生模拟**（仓库在 `<rootfs>/../tawcroot`） | 去掉开关；**清空容器时连仓库一起删** |
| 工作目录 | `-w` | 没有该参数 | 用 `sh -c 'cd … && exec …'` 兜住 |
| 只读绑定 | 不支持 | `-b SRC:DST:ro` | token 目录改成只读绑定（更贴合本意） |
| 进程模型 | tracer + tracee | **单进程** + PDEATHSIG | `killStaleDsh` / `ProcLogic` 都加了 tawcroot 判据 |

### 硬约束：插件市场必须照常能用 → 准入闸门

打开开关后，**首次启动会先在容器里跑一遍自检**（`TawcrootGate`，结论按 versionCode 缓存）：

1. **硬链接**：`ln` 后能读、`st_nlink ≥ 2` —— dsh 的原子写与 pnpm 布局都靠它；
2. **符号链接**：`ln -s` + `readlink` —— pnpm 的 `node_modules` 就是链接树；
3. **execve**：`node -e 0`、`sh -c` —— 起 node / bash 工具 / npm；
4. **/proc**：`/proc/self/status` 可读；
5. **/sdcard 绑定**：可写可读 —— 工作区与「手机文件」插件；
6. **pnpm**：已装则必须能跑 —— 插件市场的前置条件。

**任一项不过 → 自动回落 PRoot**，并把原因写进设置页
（`加速启动（tawcroot）` 下面那行会显示"自检未通过：HARDLINK_NLINK"这种可读标记）。
也就是说：**最坏情况是"没变快"，而不是"插件市场坏了"。**

### 许可（GPLv3，已按你选的"随包分发"处理）

- 二进制随 APK：`app/src/main/assets/tawcroot`（116,672 字节，静态链接 aarch64，**未修改**）；
- SHA-256 与出处写进 `THIRD-PARTY.md` 的「4b. tawcroot」；
- 许可全文：`LICENSES/GPL-3.0.txt`；
- 对应源码：上游 `v6` tag，获取/校验脚本：`tools/tawcroot/fetch.sh`，构建与差异说明：`tools/tawcroot/README.md`；
- **不想承担 GPLv3 义务**：删掉 `assets/tawcroot` 即可，代码会自动退回 PRoot（不需要改任何 Java）。

### 已知边界（写清楚，免得当成 bug）

| 边界 | 说明 |
| --- | --- |
| 没有真正隔离 | 上游 README 明说单进程设计 **可被逃逸**。我们本来就是 `danger-full-access`，但插件市场装的第三方插件因此更容易越界 —— 这是用"启动速度"换的 |
| 容器不再"接管" | PDEATHSIG：App 进程一死容器立刻跟着死，所以 `复用正在运行的容器` 在 tawcroot 下不会命中（回落 PRoot 时会照旧命中） |
| Android 12+ 子进程限制 | 上游提示 phantom process killer 会限制并发子进程；重度并行任务可能失败，切回 PRoot 即可 |
| 首次启用多花几秒 | 自检本身要起一次容器；只在首次/升级后各一次 |

### 怎么验证

1. 设置 → 打开「加速启动（tawcroot）」→ 重启 App（或让容器重启）；
2. `report.txt` 里应出现 `· ✅ 运行方式：tawcroot（自检通过；无 ptrace，预期启动更快）`；
   失败则是 `⚠️ tawcroot 自检未通过（…）→ 本次改用 PRoot`；
3. 对比 `· [启动] dsh 计时：首行 Nms · 共 N 行` 这条 —— 它才是"把插件加载进来"的耗时；
4. **插件市场回归**：装一个插件（`dshmarket` 里随便挑个纯 JS 的），确认能装、能生效；
   装不上就把开关关掉，并把 `report.txt` 发出来。

## v0.4.18-fz1

（`versionCode 69 → 70`。**手机控制这条链路本来就与 proot 无关** —— 这一版把它从写死路径里解出来，为"原生 node 运行时"铺路。）

### 先回答一个问题：换运行时，还能控制手机吗

能，因为这条链路里 proot 只负责"跑 shell 命令"，与手机控制无关：

```
agent（模型）
  │  bash 工具里敲 `phone tap 500 1200`
  ▼
phone CLI          ← 纯 HTTP 客户端（一个几十行的 Node 脚本，任何 Node 都能跑）
  │  GET http://127.0.0.1:3099/…?token=…
  ▼
手机控制桥          ← App 进程里的 Java（ServerSocket），**白名单在这里强制**
  │
  ├─ 无障碍服务（DshAccessibilityService）
  ├─ Shizuku / 直接命令后端
  └─ 截图、UI 树、按键、注入文字…
```

也就是说：真正的权限与能力全在 **Java 侧**（无障碍 / Shizuku / 白名单），
CLI 与插件只是"发 HTTP 请求"。所以就算 node 不再穿 proot，控制手机**一行逻辑都不用改**。

**唯一曾经写死的三处**，这一版全部改成"环境变量优先、老路径兜底"：

| 项 | 改之前 | 改之后 |
| --- | --- | --- |
| `phone` CLI 的 shebang | `#!/opt/node-v22.23.2-linux-arm64/bin/node`（写死容器里的 node） | `#!/usr/bin/env node`（哪个 node 都行） |
| 控制桥端口 | 硬编码 `3099`（CLI 与插件各写一份） | `DSH_PHONE_PORT`（默认 3099） |
| token 位置 | 硬编码 `/run/dsh-phone/token`（只在 proot 里有这个挂载点） | `DSH_PHONE_TOKEN` / `DSH_PHONE_RUN` 优先，再退回 `/run/dsh-phone` 与 `/sdcard/dsh/.phone-token` |

App 侧同时：

- 起容器时显式注入 `DSH_PHONE_RUN=/run/dsh-phone`、`DSH_PHONE_PORT=3099`（容器命令是 `env -i`，必须显式给）；
- **额外预置一份** `files/probe/native/bin/phone` —— 将来"node 原生跑"时把它放进 PATH 即可，
  不用再回来改安装逻辑；它的 token 直接读 App 私有目录，比绑进容器更简单也更安全。

### 插件更新：`dsh-phone` 1.0.4 → 1.0.5

插件里的端口/token 同样改成环境变量优先（两种运行时共用一份代码）。
因为判重用的是**文件名**，升级后会自动重装一次自带插件 —— 这是预期行为。

### 换成原生运行时之后，还需要处理的点（提前记下来）

| 项 | 说明 |
| --- | --- |
| `bash` 工具 | agent 跑 shell 命令仍要走容器（`proot … /bin/bash -lc`），包一层 wrapper 即可；每条命令多约 45ms，但命令次数少，不是瓶颈 |
| 路径差异 | 原生下 `/sdcard` 直接可访问（更好），`/root` 不存在 → HOME 指向 App 私有目录，profile 要迁移一次 |
| 虚拟屏 token | `VScreen` 现在写容器里的 `/run/dsh-vsd/token`，原生运行时同样要改成私有目录（同一套改法） |
| 插件市场 | 原生 npm/pnpm 可用；纯 JS 插件没问题，**带 node-gyp 原生编译的会失败** |

## v0.4.17-fz1

（`versionCode 68 → 69`。**修 0.4.16 引入的启动变慢** —— 是我把诊断放错了地方。）

### 用户反馈

> 更改后反而用时多了几秒。

对，而且这是我自己造成的：0.4.16 加的两个"诊断"都放在了**最不该放的位置**。

| 诊断 | 0.4.16 里跑在哪 | 后果 |
| --- | --- | --- |
| `logDshStateSizes()`（遍历 `.dsh/sessions` 等，上限 2 万文件） | **起容器之前**的关键路径上 | 每次启动都先付一遍遍历成本 |
| `measureLayoutOnce()`（遍历 1.2 万个依赖文件数符号链接） | 容器就绪**当刻**就在后台线程开跑 | 正撞上 WebView 加载 DSH 前端（长对话要 7~8 秒）最吃 CPU/IO 的时候 |
| `probeContainerBaselineOnce()`（在容器里跑一次 `node -e '0'`） | 同上 | **等于每启动一次就多背一次容器启动** |

也就是说：诊断本身没错，错在"它们和用户的启动抢资源"。

### 修法

| 项 | 改之前 | 改之后 |
| --- | --- | --- |
| 状态目录遍历 | 起容器**之前**同步路径 | 移出关键路径 |
| 三个诊断的时机 | 就绪即跑 | **就绪后 40 秒**、后台线程、`THREAD_PRIORITY_BACKGROUND` |
| 容器基线（要起 proot+node） | 每次启动自动跑一次 | **只在用户点「🧪 启动诊断」时跑** |
| 遍历上限 | 状态 2 万文件 / 布局 4 万文件 | 状态 3000 / 布局 6000（够用且快） |

### 设置里新增「🧪 启动诊断」

点了才会跑（约 1 分钟）：布局画像 + 状态目录体积 + 容器基线，
结果写进日志，再点「📋 复制启动日志」就能一次带走。
**它不在任何自动化路径上** —— 想诊断的时候点它，平时启动一点负担都没有。

### 一句话总结这条教训

> **诊断不能待在用户的关键路径上，也不能和"首屏加载"抢资源。**
> 0.4.16 之前 App 侧只占 3 秒，而这两个诊断把那 3 秒和页面的 8 秒都拖长了。

## v0.4.16-fz1

（`versionCode 67 → 68`。依据是用户自己做的 V8 profile —— 结论比我们之前的推断硬得多。）

### 真机 profile 说了什么

用户在隔离 `DSH_HOME` 里跑了影子实例，拿到 V8 CPU profile（窗口 64.4s，
采样本身有开销，所以只看占比）：

| self time | 占比 | 位置 |
| --- | --- | --- |
| fstat | 28.4% | 路径探测 |
| internalModuleStat | 23.8% | 路径探测 |
| lstat | 12.6% | **符号链接** |
| realpath | 4.6% | **符号链接** |
| open / existsSync / stat / close | 约 8.6% | 路径探测 |
| readFileUtf8 | 3.0% | 真的读文件 |
| compileSourceTextModule | 3.1% | V8 编译 |
| **`@deepseek-ai/dsh` 业务代码** | **5.3%** | — |

配套指标：`voluntary_ctxt_switches: 140648`（46 秒 14 万次主动上下文切换）、
`rchar 70MB / syscr 13772`、`utime 12.8s + stime 7.5s = 20.3s`（wall 42s，
差的那 20 秒就是 syscall 往返）。

**一句话**：proot 用 ptrace 拦每个路径类系统调用做翻译，每次 `stat` 都要让进程停一下；
而 Node 解析一个模块要试十几个候选路径，dsh 内核包里有 12,360 个 JS 文件。
**86% 的时间花在路径探测上，业务逻辑只占 5.3%，网络一条都没有。**

这同时解释了两件事：

- 摘掉 `dshmarket`（52 个 JS / 5.4 MB）确实从 76 → 59 秒：少了一串 stat 链，**线性收益**；
- 之前试的 `NODE_COMPILE_CACHE` 彻底无效：**proot 下缓存目录 7KB / 0 个文件**，
  等于没开。这条路可以从"待试"里划掉了。

### 本版做的两件事（都直接对着 profile 里的那 41.2%）

**① 依赖布局诊断**（每版本测一次，走 App 自己的文件 API，不穿 proot）：

```
· [布局] 依赖文件 12360 个 · 符号链接 501 个 · 合计 xxx MB（profile a/b，全局 c/d）
```

这一个数字决定两件事：`lstat + realpath` 那 17.2% 值不值得治（有链接就有），
以及扁平化（hoisted）能省多少。

**② 零符号链接时自动启用 `--preserve-symlinks`**

`lstat + realpath` 合计 17.2%，**专门**来自符号链接（Node 每 import 一次就要
lstat + realpath 一次）。当依赖目录里一个链接都没有时，`realpath(p) === p`，
这个开关不改变任何解析结果，只让 Node 跳过 realpath —— 纯收益。

反过来：**只要有符号链接就绝不加**（`--preserve-symlinks` 会让同一个包经两条
路径解析成两个实例，pnpm 布局下是已知的坑）。也刻意不加 `--preserve-symlinks-main`：
容器里的 `/opt/node-…/bin/dsh` 本身就是指向 bin.js 的链接，加了入口目录会被当成 `bin/`。

> 也就是说：这个开关是给"已经扁平化"或"本来就是 npm 扁平装"的环境自动生效的。
> 你现在 501 个链接，它不会开 —— 日志里会明确写"有 501 个符号链接 → 暂不启用"。

### 关于"再压下去"

按这份 profile，App 侧已经没什么可做了（App 自己只占启动的 3 秒，容器里我们
一行代码都不执行）。剩下的都是**容器布局与 proot 之间的结构性成本**：

| 手段 | 预计 | 说明 |
| --- | --- | --- |
| 摘不用的 bundle | 线性，每摘一个几秒 | `dsh-free-search`、`better-dsh-session-deletetool` 等 |
| `node-linker=hoisted`（501 链接 → 0） | 5~10 秒 | 要重装依赖；本版的诊断会验证链接数是否真的归零 |
| dsh 升到 0.2.2-rc.3 | 未知 | `--dump-config` 已只占 849ms，主要看有无更省的解析实现 |
| 干掉 ptrace（bionic 版 node 直跑） | 可能是数量级 | 结构性改造：容器只留 shell 工具，node 不穿 proot。风险大，另立项 |

## v0.4.15-fz1

（`versionCode 66 → 67`。三件事：长对话卡顿、通知栏去掉 Key 提示、启动不再弹框。）

### ① 长对话严重卡顿

**根因有两层**：

1. **DSH 的会话页没有虚拟列表** —— 所有消息都留在 DOM 里。几百上千条之后，
   屏幕外那些根本看不见的消息**也在参与样式计算与布局**，滚动/流式输出时越来越卡；
2. 我们注入的补丁里有几处 **O(n) 的周期扫描**，短对话无所谓，长对话里成了固定开销。

**改法**：

| 项 | 改之前 | 改之后 |
| --- | --- | --- |
| 屏幕外消息 | 参与排版/绘制 | 加 `content-visibility:auto` + `contain-intrinsic-size:auto 120px`，**跳过渲染** |
| 白屏探测（每 5 秒） | `body.textContent.length` —— 长对话里等于每 5 秒把几 MB 正文**拼一遍字符串** | 读"最后一次 DOM 变动时间戳"（O(1)）；只有页面**安静下来**时才量一次正文，且一分钟内复用 |
| MutationObserver 每批处理 | 最多 160 条，且每条都跑 `closest()` | 最多 60 条；只有 `characterData` 才做 `closest`（判断是否在输入框打字） |
| 侧边栏定位（每 2 秒） | `querySelector('[class*="sidebarCol"]')` —— **属性子串全文档扫描** | 缓存元素，只有被 React 重建时才重新找 |
| 工作区改名兜底（每 5 秒） | 每 5 秒跑几个属性子串选择器 | 20 秒一次（真正的改名由 observer 在**变动当帧**完成） |

**"列表容器"是怎么认的**（不写死 DSH 类名，换版本也不会失效）：三个条件同时成立才认领 ——
子节点 ≥ 40、确实是滚动容器、前几个子节点类名一致（是"同类项目的列表"），
取"节点数 × 可视高度"最大的那个。认错了的后果只是少优化一个容器，**不改动任何节点**。

**退路**：设置里新增「长对话渲染优化」开关（默认开）。极少数机型若出现滚动位置跳动，
关掉它刷新页面即可恢复。

### ② 通知栏不再挂「未设置 API Key」

常驻通知从 `运行中（未设置 API Key）` 改成 `运行中`。

用中转站/自定义提供方的人本来就不需要填官方 Key —— 而那条通知天天提醒一件
**不需要处理**的事，还占着一行位置。Key 状态仍可在「设置」看到，也仍然写进 `report.txt`。

### ③ 不再每次启动弹设置框

原来的行为：只要没填 Key，**每次启动**都会在容器就绪后 600ms 自动弹出「设置」对话框，
用户每次打开 App 都被挡一下。

现在：**一次都不弹**；只在**第一次**（用 prefs 记一笔）往日志区写一行提示，
之后完全静默。需要填 Key 的人点右上角「设置」即可（入口一直都在）。

### 实测数据：App 侧 3 秒，容器里 73 秒

用户（vivo V2464A / Android 16）打点：

```

+208ms   onCreate 结束（界面已可见，冷启动）
+372ms   WebView 页面加载完成
+3251ms  开始启动 dsh web（Phase 2 前台服务）

+76692ms dsh web 就绪

启动总耗时：76 秒
```

结论很明确：**App 侧只花 3 秒（还是升级后的一次性自检），73 秒全在容器里**
—— `proot → node → dsh → 加载插件` 这一段。而作者机上的基线是 10 秒，
这台机器慢了 7 倍，所以这一版做两件事：**能省的就省掉，剩下的必须能量清楚**。

### ① 容器还活着就直接接管（省掉整次 73 秒）

App 进程被系统回收时，容器里的 `proot`/`node` 经常**还活着**（独立进程，
启动代价已经付过）。而老逻辑一上来就 `killStaleDsh()` 把它杀掉、再从零起一份 ——
白扔 73 秒。

现在：

- dsh 就绪时把**带 token 的 URL** 落到 `running.url`；
- 下次启动先按它发一个本地 `GET`（**不穿 proot**，几百微秒）：
  回 200/302/303 就说明"dsh 活着、token 有效" → 直接接管，界面秒进；
- 判据用 HTTP+token 而不是 pid：pid 会被复用，而**只有我们的 dsh 知道那串 token**；
- 复用的容器每 30 秒再探一次，死了就自动回到正常启动路径；
- 探测失败就删记录、照常冷启动 —— 复用是纯优化，不影响正确性。

> 前提是"容器没被一起收掉"。如果日志里看到 `复用正在运行的容器`，
> 说明这条命中了；如果每次都是冷启动，说明系统把 proot/node 也一起清了
> （那就只能靠"别让它冷启动"）。

### ② 把 73 秒拆开：三条新诊断

| 日志行 | 回答什么问题 |
| --- | --- |
| `dsh 首行输出 Nms` | 容器+node 起来能说话要多久（proot/存储/CPU 有多慢） |
| `dsh 静默 Ns（上一行: …）` | 中间是否有**一次长时间阻塞**，以及卡在哪一行之后 |
| `dsh 计时：首行 … · 共 N 行 · 最大静默 …` | 一句话汇总：是一路慢，还是卡在某一处 |
| `[状态] sessions: N 个文件 / M MB` 等 | dsh 的状态目录有多大（会话/归档/缓存几万个文件会拖慢启动） |
| `[诊断] 容器基线：bash + node 冷启动 Nms` | **一次性**测最基础的 node 启动：>8 秒 = 这台机器的容器本身就慢 |

有了这几个数，下次就能直接判断：

- `dsh 首行输出` 就很大（>10 秒）→ **容器/机器慢**，App 侧已无可优化空间，
  只能靠复用容器或换设备；
- 首行很快、但某处 `静默 40s` → 是 dsh 的某个插件/步骤在等（那一段的上一行会点名）；
- `[状态]` 里文件数上万 → 在 App 里「设置 → 删除历史对话（含已归档）」就能明显变快。

### 顺带

`Env.isSymlink` 从 `private` 改为包级可见，供诊断遍历时跳过符号链接（避免顺着
会话目录里的链接爬到 `/sdcard` 去数几万个无关文件）。

## v0.4.13-fz1

（`versionCode 64 → 65`。修「首次初始化被打断，于是**每次启动都从头重来**」。）

### 用户日志说明了什么

真机日志（vivo V2464A / Android 16）里同时出现**两轮**初始化：

```
⏱ TIMING +4745ms  开始初始化（首次启动）
... TEST 1~6 全 PASS ...
  下载 rootfs（源 1/4）: https://mirrors.aliyun.com/...

  ⏱ TIMING +222ms  开始初始化（首次启动）      ← 新进程，T0 归零
... TEST 1 又重新跑一遍 ...
```

也就是说：第一轮**正在下载 rootfs 时进程被系统清掉**，用户再点开，第二轮又从 TEST 1 开始。
而原来的下载只要中断就**删掉半截文件、下次从 0 重来** —— 在慢网络 + 国产 ROM 后台管理下，
这等于永远装不完。用户说的"每次启动至少要一分钟"，其实是"每次都在重新装一遍，且永远装不完"。

两处根因，都已修：

### ① 初始化期间**没有任何前台服务** → 进程只是普通后台应用

首次安装要在前台跑几分钟（下载约 150MB + 解包 + npm），而这段时间原来**没有前台服务**，
`FLAG_KEEP_SCREEN_ON` 只在界面可见时有用；用户一切走/锁屏，vivo 直接把进程清掉。

现在 `startProvisioning()` 一开始就：

- **起前台服务**（通知栏显示"正在准备运行环境 · 45% · 下载 13/29 MB（锁屏也会继续）"）——
  进程被提到前台优先级，系统不再随手回收；
- **持一把 `PARTIAL_WAKE_LOCK`**（带 30 分钟超时兜底）—— 前台服务只解决优先级，
  不解决锁屏后 CPU/网络休眠；下载动辄几分钟，用户锁屏是常态。
  初始化结束立刻释放。

> 服务里用一个**独立的阶段标志**（`MainActivity.isInstalling()`）判断要不要让路：
> 初始化的最后一步"起 dsh web"正需要服务去起容器，只看"是否在初始化"会互相等到超时。

### ② 下载不支持续传 → 一断就白下

`download()` 现在带 `Range` 断头续传：

| 情况 | 以前 | 现在 |
| --- | --- | --- |
| 下到 20MB 进程被杀 / 断网 | 删掉 `.part`，下次从 0 | **保留，下次从 20MB 接着下** |
| 换镜像 | — | 按 `.part.meta` 里的源名**主动丢弃**，绝不把两个镜像拼成坏包 |
| 服务端文件变了 | 无感知 | `.meta` 记着总大小，对不上就重来 |
| 服务端不支持 Range（回 200） | — | 自动退回"从头写"，不影响正确性 |
| 收到的比声明的还多 | — | 判定脏数据，当场丢弃 |

Node 归档的下载、以及首次安装时"后台预取 Node"那条路，用的是同一个函数，一并受益。

### 顺带修掉的两个诊断问题

- **TIMING 出现时间倒流**（日志里 `+4745ms` 后面跟着 `+222ms`）：基准原来用
  `System.currentTimeMillis()`，而开机后不久系统会用 NTP 校时、把墙钟往前拨。
  改用 `SystemClock.uptimeMillis()`（单调），启动耗时才是可信的。
- 通知栏现在能看到真实进度（百分比 + 已下/总 MB + 当前步骤），锁屏也不影响。

### 装上这一版之后怎么确认

首次安装时：通知栏应出现"正在准备运行环境 · N%"，**锁屏也不会停**；
`report.txt` 里如果看到 `断点续传：从 N MB 处继续`，说明上一次的进度被接上了。

## v0.4.12-fz1

（`versionCode 63 → 64`。修一个**启动被网络拖住**的问题。）

### 修「每次启动至少一分钟」：pnpm 安装被挪出启动路径

**现象**：用户实测每次启动都要一分钟以上，而设计值是 8~12 秒。

**根因**：`Env.ensurePnpm()` 在 pnpm 缺失时会在容器里跑 `npm i -g pnpm` ——
一次真实下载，超时上限 **240 秒**。而它被**同步**放在"起 dsh 之前"：

```
startDsh() → 前置并行 → ensurePnpm()  ← 卡在这里等网络
           → 起 dsh 进程 → 等 URL → 界面
```

网络慢、或连不上 npm registry 的机器上，每次启动都要先等它失败；
更糟的是**装不上就下次还试** —— 于是"每次启动至少一分钟"，而且永远好不了。

**修法**：

| 项 | 改之前 | 改之后 |
| --- | --- | --- |
| pnpm 安装时机 | 起 dsh **之前**（阻塞） | dsh 起来**之后**（后台线程） |
| 失败重试 | 每次启动都试 | 退避 **6 小时** |
| 已装好时 | 一次文件检查 | 一次文件检查（连线程都不起） |
| 前置并行等待上限 | 120 秒 | **30 秒** |

pnpm 只被「插件市场」用到（`dsh plugin add` 内部转发给它），和"界面能不能用"无关 ——
所以它晚几十秒没有任何影响。**代价**：首次启动后的一小段时间里，
插件市场可能提示不可用，装好后自动可用；其它功能完全不受影响。

### 顺带：让"启动慢"这件事以后能一眼定位

- `report.txt` 新增一行 **`⏱ 启动总耗时（进程启动 → dsh 就绪）：N 秒`**
  （基准用 `Process.getStartUptimeMillis()`，也就是用户点图标那一刻，不是类加载）；
- 设置里新增 **「📋 复制启动日志（排查启动慢）」** —— 原来"复制日志"只在
  **失败面板**里，而启动慢的时候界面是正常的，用户根本找不到那个按钮；
- 前置四组并行、pnpm、拉起 dsh 进程、dsh 就绪，每一段都有毫秒数写进日志。

> 如果更新后仍然慢，请点「设置 → 📋 复制启动日志」把内容发出来。
> 里面这几行能直接指出时间花在哪：
> `前置并行完成 Nms（proot … · 手机桥 … · 插件 … · 挂载点 …）`、
> `拉起 dsh 进程 Nms`、`dsh 就绪`、`启动总耗时 N 秒`。

## v0.4.11-fz1

（`versionCode 62 → 63`。**这一版只改启动路径，不动任何功能行为**。）

主题：**启动速度**。先说结论，再交代每一项的依据和实测数据。

| 场景 | 改之前 | 改之后 | 省下 |
| --- | --- | --- | --- |
| **热启动**（划掉任务再点开 / 系统重建界面 / 从别的 App 切回后重建） | 约 **4.1~4.4 秒** | 约 **0.6~0.8 秒** | **≈3.5 秒** |
| 冷启动（容器要从头拉起） | 约 10.1~11.5 秒 | 约 **8.3~9.7 秒** | ≈1.7~1.8 秒 |
| 首次安装（rootfs + Node 下载） | 两段下载串行 | 两段并行 | 一次完整下载的时间 |
| 冷启动期间的 CPU 占用 | 开屏 60fps 全屏重绘 8~12 秒 | 分镜播完即停心跳 | 一个持续重绘线程 |

> 数字的来源见下面每一条。**热启动那一行是这次的主要收益** ——
> 冷启动的大头（`dsh web` 自己起 node、加载几百个插件）在 App 这一侧改不动，
> 详见最后一节「没做（以及为什么）」。

### ① 热启动不再硬等 3.4 秒开屏（主要收益）

原先不管什么情况，开屏都至少显示 3.4 秒（播完"点→线→面"分镜）+ 0.76 秒收尾倒放。
它存在的理由本来是**陪用户等容器启动**（8~12 秒）—— 那种情况下它一分钱不浪费。

但"容器其实早就在跑"的启动方式很常见：前台服务还活着、`DshService.getUrl()` 已经有值，
页面 0.3~0.5 秒就能画出来。此时那 3.4 + 0.76 秒就是**纯等待**：

- 划掉最近任务再点开（前台服务会活下来，容器不会重启）；
- 系统回收 Activity 后重建；
- 从别的 App 切回来后界面被重建。

现在的判据是一行静态字段读取（`DshService.getUrl() != null`）：
热启动只留 `WARM_SPLASH_MIN_MS = 200ms`（盖住首帧、不闪黑屏），
并且**跳过收尾倒放**（没有等待就没有要收的尾），用 260ms 淡出接棒。

> 冷启动不受影响：分镜照旧完整播完。只改了"开屏最短时长"和"要不要播收尾"两处，
> 见 `MainActivity.splashMinMs / WARM_SPLASH_MIN_MS / WARM_READY_HOLD_MS`。

### ② 等容器地址的轮询：1 秒 → 100 毫秒

`awaitUrl()` 以前每秒看一眼"前台服务有没有解析出地址"。地址在第 10.11 秒就绪、
界面却要到第 11.0 秒才开始加载 —— 平均白等 0.5 秒、最坏 1 秒，全算在用户头上。

现在 100ms 一轮（循环体只是读一个 volatile 字段），同时把"20 圈 = 20 秒"的超时判据
改成按**时间**算，并把界面读数节流在 500ms（`AWAIT_UI_TICK_MS`）——
轮询变密不会让状态栏变成高频重排。

### ③ 前台服务的启动前置工作改成并行

`startDsh()` 里那几件事（解 proot 和两个 .so、装 phone CLI / AGENTS.md、摘桌宠、
装自带插件、mkdir 共享存储）**互不依赖**，原来是串着做的，每一件都要碰手机存储。
现在分成四组并行，全部 join 完才起容器（"起 dsh 前一切就绪"这个前提没变）：

| 组 | 内容 | 为什么不能拆更细 |
| --- | --- | --- |
| A | `prepareProot` | 起容器、装 pnpm 都要它 |
| B | 手机控制桥 + phone CLI / AGENTS.md | 独立的资产拷贝 |
| C | 摘桌宠 + 装自带插件 | **两者都改同一个 package.json**，必须串行 |
| D | 挂载点 / 工作区 | 独立 |

每一组的耗时都会写进 `report.txt`：
`· [启动] 前置并行完成 XXms（proot 8 · 手机桥 21 · 插件 15 · 挂载点 30，最慢的一组算总耗时）`。

### ④ 首次安装：rootfs 与 Node 并行下载

原来 TEST 7 下 rootfs（约 30MB）并解压完，TEST 8 才开始下 Node（约 50MB）——
一次安装里两段下载串着等。它们互不依赖，现在 rootfs 一开始下，Node 就在后台线程下：

- 预取落到 `NODE_DIR.prefetch`（**永不与主流程写同一个文件**，主流程完成后 rename 接管）；
- 主流程最多等它 20 秒，等不到就放弃、自己下（首次安装绝不能被后台任务卡住）；
- 预取失败只写日志，不改变主流程判定（主流程本来就有多源重试）。

### ⑤ 开屏：去掉旋转的立方体，等待期彻底停掉 60fps 心跳

按用户要求去掉开屏上那颗"一直在转的线框立方体"。它本来是等待期唯一的动效，
去掉之后画面在分镜播完（1.65 秒）后就**完全静止** —— 于是：

- 分镜播完立刻 `cancelTicker()`，等待期不再请求任何一帧；
- 画面更新改为"进度变了才画"（`setProgress()` 自己 invalidate，实测 500ms 一次）；
- 收尾倒放开始时再 `startTicker()` 恢复逐帧（那 1.15 秒仍是 60fps）。

意义不只是省电：容器启动那 8~12 秒正是 node 加载几百个插件最吃 CPU 的时候，
以前开屏在跟它抢同一个 CPU/GPU。

### ⑥ 新增 GitHub 编译工作流（不需要任何 secret）

`.github/workflows/build.yml`：push 到 `main` 或 `perf/**`、或手动触发，都会编出
**可安装的 debug APK** 并作为 artifact 上传（debug 包由 AGP 自动生成的 debug keystore 签名）。
有 `DSH_KEYSTORE_B64` secret 时顺带再出一个签名 release 包并独立验签。

这样"改完能不能编过"不必依赖本地环境；`release.yml`（打 tag 发版）保持原样不动。

### ⑦ 冷启动"最后一公里"：就绪后还要干等的那 1.65 秒

冷启动的最后一段一直被忽略：服务就绪 → 页面加载完（约 0.4 秒）→ **揭幕**。
而揭幕要求"收尾倒放播完"，于是：

| 段 | 改之前 | 改之后 |
| --- | --- | --- |
| 就绪后先停一下（给"100% 已就绪"读数看） | 500ms | **120ms** |
| 收尾倒放（此时页面**已经画好了**，倒放遮的是一个完成品） | 1150ms | **600ms** |

两处合计省 **≈0.9 秒**。它们不影响分镜（"点→线→面"仍是 1.65 秒完整播放），
只砍掉"页面早就能用了、动画还在前面挡着"的那一段。

### ⑧ 容器提前到 Application 里启动

原来容器要等 `MainActivity.onCreate` 把整套界面搭完（真机 100~300ms），
再由初始化线程 `startWebAndWait() → startDshService()` 拉起来。
现在 `DshApp.onCreate`（进程起来后的第一站）就把前台服务叫起来 ——
容器 boot 是本 App 启动耗时的主体（8~9 秒），让它早开始 100~300ms，
用户就早 100~300ms 看到界面。

只改"什么时候开始"，不改"怎么开始"：服务本身幂等（`isAlive()` 门槛），
Activity 后面照旧调用 `startDshService()`，不会起第二个容器。
容器没装好时这里**什么都不做**（首次安装仍由初始化流程负责），
异常全部吞掉（这里在最前面，抛出去就是启动崩溃）。

### 没做（以及为什么）—— 免得下次再走一遍

冷启动那 10 秒里，App 自己只占 0.1~0.3 秒，剩下全在容器里：`dsh web` 起 node、
加载几百个 JS 模块。下面这些都**实测过**，但**没有采用**：

| 试过的方案 | 结论 |
| --- | --- |
| `NODE_COMPILE_CACHE`（V8 字节码缓存） | dsh 是纯 ESM，**Node 22 的编译缓存只覆盖 CJS**：实测缓存目录只有 8K、启动时间无变化 |
| `--max-semi-space-size=32` / `--v8-pool-size=1` 等 GC / 线程调参 | 5 次取中位数：基线 2902ms，semi32 **更慢**（3269ms），pool1 无差别 → 不加 |
| 升级 Node 到 24+（ESM 编译缓存） | 会换 ABI，容器里已装的 native 依赖要全部重装，且无法在没有真机的情况下验证 → 不做 |
| 预读 node_modules 给 page cache 预热 | 省的是磁盘读，而真正的大头是 proot 对每个系统调用的拦截；抵消后收益不明 → 不做 |
| 复用"还在跑的容器"以跳过重启 | Android 的 LMK 会把同 oom_score_adj 的 proot/node 一起收掉，实际几乎没有命中场景 → 不做 |
| **开机自启/开机预热容器**（把冷启动整体挪到开机后） | 实现过（`BOOT_COMPLETED` 里起前台服务，能把 11 秒变 0.7 秒），但**用户明确要求不要开机自启动** → 已撤除，不留权限、不留 receiver |
| `--preserve-symlinks` 减少 realpath 系统调用 | dsh 的 profile 依赖 pnpm 风格的符号链接布局，改这个有解析错乱风险 → 不做 |

### 怎么验证这次的改动

启动后看 App 私有目录里的 `report.txt`（`adb exec-out run-as com.dsh.tdsh cat files/probe/report.txt`），
里面现在会多出这几行：

```
⏱ TIMING +Nms  onCreate：热启动（容器已在跑）      ← 热/冷一目了然
⏱ TIMING +Nms  awaitUrl 拿到地址（自等待起 Nms）   ← 轮询浪费了多少时间
  · [启动] 前置并行完成 Nms（proot … · 手机桥 … · 插件 … · 挂载点 …）
  · [启动] pnpm 检查 Nms
  · [启动] 拉起 dsh 进程 Nms
⏱ TIMING +Nms  WebView 页面加载完成
```

热启动应该看到 `onCreate：热启动` 且 `awaitUrl 拿到地址` 只有个位数毫秒。

### 「进不去就自动停用第三方插件」—— 现在真的自动了

**改之前（0.2.2 ~ 0.2.6）**：所谓"自动"只做了一半 ——

| 第几次失败 | 以前的行为 |
| --- | --- |
| 第 1 次 | 只弹一个自救面板，要用户**看懂并点**「停用并重启」 |
| 第 2 次 | 才自动进安全模式，但**仍然要用户点一下「重启」** |

而用户此刻面对的是一屏白：让他先读懂面板、再点按钮，本身就是负担。
更别说面板上还有三个按钮要选。

**改之后（0.2.7）**：**第一次上报就动手，不用点任何东西** ——

1. 上报文本里**点名了**某个插件（`xxx: pending (waiting for service: …)`）
   → 只停它，最精准；
2. **没点名**（比如"空白 25 秒"这种没有任何文字的上报）
   → 停掉**全部第三方插件**（等价于安全模式）；
3. 然后**自动重启** DSH —— 界面自己回来。

停用清单记在 App 的 prefs 里，包目录也真的挪到了 `.dsh-disabled/`，
所以「手机权限 → 插件安全模式」点一下就能恢复（见 0.2.3 的修复）。

**为什么必须有"最多自动动手 2 次"的上限**：如果界面起不来**根本不是插件的问题**
（容器坏了 / 网络断了 / 版本不匹配），那"停用插件 + 重启"永远不会成功 ——
没有上限就是**无限重启**，用户会看到界面一直闪、插件还一个个消失。
超过上限就停止自动动手，改成亮面板把决定权交回用户，
并提示「手机权限 → 复制运行日志」。

**顺带的加固**：`dsh-phone-files`（自带的手机文件插件）也加进了"受保护"名单 ——
它是 App 自带的、已知可用的，不该被自救停掉。

**怎么验证的**：往 profile 里塞一个**真正会卡住界面的第三方插件**来复现用户场景 ——
`node_modules/dsh-test-bad`（有 `package.json` / `cordis.patch.yml` / `lib/*.js`，
服务端能正常加载，**客户端 `inject = ["slots","settingsScope"]` 等一个 0.2 里
已经不存在的服务**），并把它登记进 `dsh.profile.bundles` 与 `dependencies`。
这就是用户截图里那个报错形态。然后**全程不做任何操作**，只看 App 自己干了什么。

### 平板：**会话列表现在默认可见**

**用户反馈**：平板上界面还是原生 DSH —— 找不到会话列表。
（设置入口那条在 0.2.4 已修，这一版修的是会话。）

**先把 DSH 在平板上的真实行为量清楚**（`wm size 1600x2560` + `density 320`，
逻辑宽 800dp，就是绝大多数平板竖屏那一档）：

| 逻辑宽度 | 侧边栏 | 会话行 |
| --- | --- | --- |
| 360dp（手机） | 抽屉，点左上角鲸鱼唤出 | 抽屉打开后有 |
| **800dp（平板竖屏）** | **56px 的图标轨道** | **0 条 —— 根本没进 DOM** |
| 1707dp（平板横屏 / 大屏） | 280px 的完整侧边栏 | 5 条都在 |

三个关键结论：

1. 中间那一档 DSH 只给一排图标（新建会话 / 插件 / 添加工作区 / 搜索会话 / 设置），
   **没有任何会话列表** —— 用户连"怎么换会话"都找不到；
2. `localStorage` 里**没有**任何"侧边栏展开/收起"的开关 ——
   这是 DSH **按宽度**做的响应式行为，不是"状态被收起了"；
3. 因为会话行**压根没渲染**，纯 CSS 救不回来（隐藏和没渲染是两回事）。

**怎么解决的**：侧边栏里有一个 `aria-label="打开侧边栏"` 的按钮，
大小是 **0×0（完全看不见）**，但**点它真的有效** ——
实测点一下侧边栏立刻 `56 → 280px`、会话行 `0 → 5`。
所以补丁现在会在**宽屏（≥700px）**下、页面加载后点它一次，把完整会话列表带出来。

**有意只点一次（最多 3 次兜底）**：用户手动收起侧边栏是**有意的**，
不能每次 DOM 变动都抢回来 —— 那会变成"我一收它就自己弹回来"。
手机上这个函数直接退出：窄屏抽屉本来就该是收起的（那是 `patchSidebar` 的活）。

**真机实测**：

| 场景 | 结果 |
| --- | --- |
| 平板 800dp（`wm size 1600x2560` + `density 320`） | ✓ **加载即展开**：左侧 新会话 / 插件 / 工作区 `root` + 4 个会话 + 设置；右侧对话区仍然舒适 |

## v0.2.5

（`versionCode 28 → 29`，同签名，可直接覆盖安装。）

### 「选完文件，什么都没加上」—— 0.2.4 只修了一半

**实地证据**（用户发来的两段录屏）：点 `+ → 文件`，打开的是
**vivo 的「安全访问」选择器**（不是标准 DocumentsUI），在里面选中一张 JPEG，
点**「确定」**，回到界面 —— **输入框空的、没有任何报错**。
另一段录屏里用户还在分类里翻找（图片分类是空的），最后也没能加上。

**0.2.4 的缺口**：那一版是"先探测这个 URI 读不读得到，读得到就直通"。
可是 —— **探测跑在应用进程里，真正去读它的是 WebView 的渲染进程**。
云盘 / 相册 / 厂商安全选择器给出的 `content://` 很多是"只有收到选择结果的
那个进程能读"：应用进程探测通过，渲染进程照样打不开；
而 **WebView 读不到内容时不会报错，它只是当作用户什么都没选**。
于是现象就和"点了没反应"一模一样。

> 这个坑不是我们独有的：公开的 WebView 封装库里也有同一个修复
> ——"把选中文件的 content URI 复制到 app 私有缓存后再传给 WebView，
> 解决云盘、系统相册、媒体库等 URI 渲染进程无法读取导致上传内容为空的问题"。

**修法**：不再探测，**一律拷贝**。

1. 内容先落到 `cache/attach/<毫秒>/<原文件名>`；
2. 交给 WebView 的是**由本 App 自己的 FileProvider** 提供的 `content://`
   —— 读它走的是我们自己的进程，跨进程授权问题从根上消失；
3. 拷贝放**后台线程**（几十 MB 的文件在主线程上拷会把界面卡住甚至 ANR）；
4. 超过 **100MB** 不拷贝、直接直通（不给一个大视频白等好几秒）；
5. 副本**每天清一次**（否则会悄悄吃掉几百 MB，而 cache 用户既看不见也清不掉）；
6. 文件名**保持原样**。之前叫"时间戳_原名"，而那串时间戳会显示在附件卡片上
   （界面取 URI 最后一段），看着就像出了 bug。

**真机实测**（vivo V2408A / Android 16）：

| 场景 | 结果 |
| --- | --- |
| 图片（104KB jpg） | ✓ 输入框出现缩略图 · `cache/attach/1790818656547/DSH-arrow-4x3.jpg` |
| 视频（**32MB** mp4） | ✓ 卡片显示 `Lv_0_20261001025450.mp4 / MP4 31MB`（名字干净） |
| 报告文件 | ✓ `[附件] 已拷贝进 cache 再交给界面：content://com.android.providers.media.documents/document/…` |

**必须说清楚的一点**：用户那台机器上的 vivo「安全访问」选择器，我这边**复现不出来**
（本机即使撤销存储权限，出来的仍是标准 DocumentsUI）—— 那是 ROM 版本差异。
所以 0.2.5 是**按机制修的 + 针对性兜底**，不是"在出故障的那台机器上验证过"。
为此专门加了 `[附件]` 诊断行（写进报告文件，「复制日志」一次带走）：
万一 0.2.5 之后还有人报加不上，日志能直接看出卡在哪一层、选择器返回了什么。

### 一、「停用插件」之前**根本没有停用** —— 这次是真停了

**用户原话**：安全模式的停用功能并不存在，不能真的停用。

**现象**：在「插件安全模式」里点了停用，插件照旧被加载，界面照旧卡在白屏。

**根因**：0.2.2 只做了一件事 —— 把包名从 profile 的 `dsh.profile.bundles` 里删掉。
但 `bundles` 只是"加载清单"，DSH 还会按 `dependencies` 和自己的库存把包找回来。
**配置里少一行 ≠ 它不被加载。**

**修法**：停用一个插件，现在同时做三件事：

1. 从 `dsh.profile.bundles` 摘掉（决定加载谁）；
2. 从 `dependencies` 摘掉 —— 原来的声明记在 App 的 prefs 里，恢复时**照原样写回**；
3. 把 `node_modules/<包名>` **整个目录挪到** `node_modules/.dsh-disabled/` ——
   包目录都不在了，它没有任何可能被加载。

「恢复全部」做的是逆操作：目录挪回原位 + 依赖声明写回。
**挪走而不是删除**，所以"回退到装插件之前"是真的能回去的。

**真机实测**（vivo V2408A / Android 16）。为了测到这条路径，往 profile 里登记了一个
**真实存在目录、但内容为空**的假插件 `dsh-debug-hang`（复现"第三方坏插件"），
然后**走界面点**，看 logcat（tag `DSH_SAFEMODE`）：

| --- | --- |

| 界面点「插件安全模式 → 恢复全部」 | **`挪回包目录 dsh-debug-hang → true [坟场里还有=false 原位目录在=true]`** |
| 清理测试插件后重启 | `现 bundles=[dsh-base, dsh-web-app, dsh-phone, dsh-phone-files] · 待恢复=[]` → `就绪: http://127.0.0.1:3080/` |

`源还在=false` / `原位目录在=true` 这两项是关键：它们说明**目录真的被移走了、又真的被移回来了**，
而不只是配置里改了一行。

### ① "新版本环境装不上" —— 下载不校验 + 坏包被反复使用

**现象**（用户截图）：初始化跑到 4 分 20 秒，满屏 `proot error: '/usr/bin/env' not found`，

1. **下载从不校验字节数**。`download()` 拿到了 `Content-Length` 却**从不比对** ——

   而"归档是否可用"的检查只有 `> 20MB`（真实包 29.9MB），半截包轻松过关。
2. **只看 `/usr/bin/bash` 就判定"装好了"**。归档按**字母序**解压，
   `usr/bin/bash` 排在 `usr/bin/env` **前面** —— 解压中断（截断包、或存储空间不足）
   恰好停在这一段时，bash 在、env 不在，于是每次重试都"跳过下载解压"，
   然后在 proot 里报 `'/usr/bin/env' not found`，Node/npm 必然全崩。

**这就是"装不上、点重试也没用"的完整链条**，而且那屏日志（npm 失败、node 自检失败）
指向的方向完全是错的，白等好几分钟。

**改了四处**：

- 下载**必须字节数一致**（服务器给了 `Content-Length` 就一个字节不能差；
  没给就不得小于已知体积），任何中途失败都删掉 `.part`，绝不留半截文件；
- rootfs 解压后**核对 6 个关键文件**（`env`/`bash`/`bin/sh`/`os-release`/libc/apt），
  不通过就**丢掉重下**，并逐个源重试 —— 死循环从这里被打破；
- **空间预检**：装之前先看可用空间，不够就直说"可用 X MB，至少需要 Y MB"，
  不再把"没空间"伪装成"下载失败"；
- 容器没装好就**到此为止**：不再往下跑 TEST 8~11 和 Phase 2，日志直接指向真正的原因。

顺带修掉一个**已经 404 的备用源**（清华 `nodejs-release`，2026-09 复测），
换成了阿里云 + 中科大。`Env.isInstalled()` 也补上了 `/usr/bin/env` ——
否则"快速启动"这条捷径会跳过自检，直接带着坏容器进 proot。

### ① 返回键：在插件页按返回，**插件页现在真的退得掉**

**问题**（用户反馈 + 截图）：在插件页按返回，抽屉是拉开了，**但背景还是插件页**。

**根因**（真机实测，不是猜的）：插件页占的是**中间栏**，而 DSH 在插件页打开时
**不给任何会话行打 `aria-selected`** —— 进插件页后抽屉里那几行**全都不高亮**。
于是返回键处理里再问"当前会话是谁"已经问不出来，只能走进"把抽屉拉开、让用户自己点"
的安全退化。**这就是"按返回了背景还是插件页"的直接原因。**

> 更早那版"自动切走再切回"失败是另一个原因：回切时拿 `innerText` 前 24 个字去比，
> 而**相对时间会变**（"刚刚" → "1天"），一比就比不中，插件页顶不掉。

**修法**：趁**还能看到高亮**的时候（每次界面刷新都会跑 `apply()`）把当前会话记下来 ——
`rememberCurrentSession()` 存三样，按可靠性依次用：

1. **DOM 节点本身** —— React 按 key 复用元素，切走再回来还是同一个；
2. `data-row-key`（形如 `session:<uuid>`）；
3. **标题前 8 个字** —— 只取标题、**不碰相对时间**（时间会变，标题不会）。

插件页按返回就依次做三件事：**切到另一条会话把插件页顶掉 → 切回记下的那条 → 收起抽屉**。
全程用 `__dshHoldDrawer` 压住"点会话就收抽屉"，只在最后收一次，不会出现
"抽屉先回去、又弹回来、再跟对话一起收"。没有别的会话可中转、或会话行还没渲染出来时，
**安全退化**成原来的"只拉开抽屉"，绝不把返回键弄坏。

**真机实测**（vivo V2408A / Android 16，release 包，跑了两轮）：

| 场景 | 结果 |
| --- | --- |
| 在「用心理学传播学帮想回复」里进插件页 → 按返回 | 插件页消失，回到**同一个**会话 ✓ |
| 先切到「Termux 运行环境确认」再进插件页 → 按返回 | 回到 **Termux**（记住的是最后一次选中的会话）✓ |
| 进插件页时 | 抽屉自动收起、「添加插件」完整可见、鲸鱼隐藏 ✓ |
| 返回全程 | 抽屉只在最后收一次，没有来回弹 ✓ |

> 顺带说明：切换会话后 DSH 自己会聚焦输入框、键盘弹出 —— 真人点会话切换也一样，
> 不是这次改动引入的。

### ② 文档版本号跟进

`安装与使用说明.md` 里的文件名与末尾版本标注从 `0.1.21` 更新为 `0.2.0`。

## v0.1.18

**内核升级**：检测到旧版本 → 提示 → 一键升级。
这一版发布前已经**在本机实战升级过一次**（0.1.5-rc.3 → 0.2.0-rc.2）。

### 为什么需要它

App 装容器时执行的是 `npm install -g @deepseek-ai/dsh`（**不锁版本**）。
于是"装完那一刻是哪版，就永远停在哪版" —— 上游发新版，用户完全不知道，
只能卸载重装。这一版补上检测 + 一键升级。

### 检测怎么做的

| 要读的东西 | 从哪读 | 为什么 |
|---|---|---|
| 已装版本 | **直接读 rootfs 里的 `package.json`** | 不用起容器，几毫秒出结果。起一次 proot 要几百毫秒到几秒，检测不该那么贵 |
| 最新版本 | npm registry 的 `-/package/@deepseek-ai%2Fdsh/dist-tags` | 这个端点只回三个标签（latest/next/alpha），比拉整包文档小得多；带 6 小时缓存 |

版本比大小按 semver 的规矩：**带预发布后缀的算更小**
（否则 `0.2.0-rc.2` 会被判成大于 `0.2.0`，那就永远"有更新"）。

界面上把 **next / latest 两个通道都摆出来**，默认跟最新 ——
让用户看得见自己装的是 pre-release 还是稳定标签，而不是我们替他决定"最新就是最好"。

就一条：容器里 `npm install -g @deepseek-ai/dsh@<版本>`。但有两个坑：

1. **必须异步。** 升级要 2~8 分钟，而控制桥的 HTTP 请求 25 秒就超时
   （`REQUEST_TIMEOUT_MS`）。同步跑的结果是"桥说超时、其实还在装"，比不报还糟。
   所以 `op=run` 只踢一脚就返回，进度靠 `op=status` 轮询。
2. **装完必须核对版本。** 拿 `dsh --version`（同样是直接读文件）读回来比对，
   不对就报错。"装完就当成功"是最难排查的状态。

升级成功会自动重启内核（`DshService.requestRestart()`）。

## v0.1.17

三件事：**返回键不再一按就退出**、**白名单一键添加**、
以及给本地代理（CLIProxyAPI 那类）做的**容器常驻服务**。

### ① 返回键：分层返回

**问题**：App 原来**完全没有接管返回键**，于是走系统默认 = 结束 MainActivity ——
用户看到的就"按一下返回，整个界面没了"，而不是"关掉当前这一层"。

**改法**：`onBackPressed()` 先问页面（注入脚本里的 `window.__dshHandleBack`）
有没有东西可关，由内到外一层层退：

```
设置分类详情 → 设置弹窗 → 其它模态浮层（图片大图等）→ 右侧栏 → 左侧抽屉
```

全都关完了才轮到 App —— 而且**再按一次**才真退出，免得手滑一下就没了。

**实测**（设置弹窗开着时按系统返回键）：

| 操作 | 结果 |
|---|---|
| 第 1 次按返回 | 弹窗关掉，**App 仍在前台**（原来这里就退出去了） |
| 第 2 次按返回 | 仍在前台，只提示"再按一次返回退出" |
| 连按两次 | 退到桌面 ✅ |

### ② 白名单一键添加

**问题**：agent 被白名单拒绝后，用户要自己走六步 ——
设置 → 手机控制 → 应用白名单 → 在一长串应用里翻找 → 勾上 → 保存。

**改法**：被拒时顺手发一条通知：「DSH 想操作「设置」」，
带一个**「加入白名单」**按钮，点一下就把当前前台那个应用加进去并保存，
回来让 agent 重试即可。同一条通知 30 秒内不重复打扰（agent 常常会连着重试）。

另外「手机控制」页加了一个按钮：**「把「XX」加入白名单」**，
取的是"上一个不是本 App 的前台应用" —— 用户在设置页里点时，
前台其实是 App 自己，直接取当前前台只会拿到 `com.dsh.tdsh`，毫无用处。

> 边界没有放宽：这只是把"同意"从六步压成一步，**加不加仍然由用户点那一下决定**。

**实测**：切到不在白名单的「设置」→ `/ui` 返回
`不在白名单里，已拒绝（已发一条通知，点一下就能把它加入白名单）`，
`dumpsys notification` 里能看到 `dsh_whitelist` 频道那条通知，
标题 `DSH 想操作「设置」`、动作 `加入白名单`。

### ③ 容器常驻服务：给本地代理用（CLIProxyAPI 这类）

**要解决的是什么**：CLIProxyAPI 这类本地代理**必须先跑起来客户端才连得上**，
而它自己不出回答、只负责转发 + 管账号池 —— 也就是说它是**被调用方**，
没有任何"启动键"能从客户端那头按下去。在电脑上它是个常驻服务，
在手机上却变成"每次都得手动拉一次"，于是有了那个很别扭的绕法
（切到别的模型借一次请求把它唤醒，再切回来）。
解法只有一个：**让它常驻**。

**做了什么**：App 设置里新增「常驻服务（本机）」，配一条启动命令即可：

- 容器就绪后**自动拉起**；
- 每 60 秒检查一次，**挂了自动重拉**（连续失败 5 次就停手，免得白烧电）；
- **重复启动是幂等的**，不会越开越多份。

**两个关键实现细节**（都是踩出来的）：

1. **不能带 `--kill-on-exit`。** 容器命令默认带这个参数（"主命令退出时一并收掉
   残留子进程"），对一次性命令是对的，但常驻服务恰恰要反过来 ——
   带上它，`nohup ... &` 起来的服务会在启动器退出那一刻被收掉，
   表现就是"启动成功了，一秒后进程没了"。
2. **不能用"等进程结束再读输出"那套。** proot 是整棵进程树的 ptrace 监督者：
   只要后台服务还活着，启动它的那个 proot **就不会退出**。
   实测同时踩到"启动超时"和"服务其实在跑"两个矛盾现象 ——
   因为超时后的 `destroy()` 会把监督者杀掉。
   现在只等回执（STARTED / ALREADY / DIED），拿到就撒手，绝不 destroy。

还有一点：容器里的进程**能活过 App 重启**（实测 dsh web 在 force-stop 之后还在跑），
所以判断"在不在跑"不能靠内存里的 Process 句柄，否则每次启动 App 都会再拉一份、
代理立刻端口冲突。现在用**容器内的 PID 文件**（`/tmp/dsh-svc-<id>.pid` + `kill -0`），
跟 App 的生命周期完全解耦。

**实测**：

| 操作 | 结果 |
|---|---|
| 配一个 `sleep 600` 并启动 | ✅ 运行中 |
| 杀掉它 → 等 75 秒 | ✅ 看护自动重拉（日志：`看护重启 [测试常驻]（第 1 次）: 已启动`），pid 变了 |
| App 重启后再查 | ✅ 认得出它还在跑（pid 一致），**没有重复启动** |
| 再点一次"启动" | ✅ 报"本来就在跑" |

agent 也能用 `phone services` 查看/配置（`/services?op=status|add|remove|restart`）。

## v0.1.16

两件事：**启动快了一截**，以及把**麦克风到底卡在哪**钉死了。

### ① 启动时间：16.5 秒 → 10.1 秒

先说结论：**慢的不是自检，是容器**。被质疑过的那 11 项自检全跑完只要 **1.7 秒**，
真正的大头是 `dsh web` 自己启动要 **10~14 秒**。

**怎么量的**：在 App 里打点（类加载时为 t0，每个阶段写一行到 `report.txt`）——
之所以不用外部掐表，是因为这台机器上"进程到底是不是新起的"很难从外面判断
（前台服务 + 厂商保活会让测量对象飘，我量出过自相矛盾的数字）。
而 logcat 也不能用：OriginOS 会把缓冲清掉，实测整个 buffer 只剩 116 行、
我们自己的一行都不剩。所以打点**落文件**。

冷启动实测（每次都先把容器 `proot`/`node` 杀掉）：

| 里程碑 | 优化前（完整自检 + 关掉 seccomp） | 优化后（快速路径 + seccomp） |
|---|---|---|
| 界面可见 | 103 ms | 113 ms |
| 开始启动 dsh web | **1835 ms** | **114 ms** |
| dsh web 就绪 | 15840 ms | **10113 ms** |
| WebView 页面加载完成 | 16508 ms | **10500 ms 左右** |

两处改动：

**a. 快速路径：装好了就别再自检一遍。**
那 11 项探针每一项都要起一次 proot（有的还要起 node），而它们全部跑完
才会轮到启动 `dsh web`。现在只要"容器就绪 + 上次自检标记有效"就直接跳到启动，
省掉 1.7 秒。标记文件里写的是 **versionCode**，所以升级 App 后会自动完整自检一次；
手动点「重试」也会强制完整自检（用户是出问题了才点的，不能被标记糊弄过去）。

**b. 打开 proot 的 seccomp 加速。**
`Env.buildProcess()` 里原本写着 `PROOT_NO_SECCOMP=1` ——
意思是"关掉 seccomp、只用纯 ptrace"，于是**每一个系统调用**都要陷入 ptrace
再被翻译一遍；而 `dsh web` 启动要读几百个 JS 文件。去掉之后冷启动稳定在
**10.11 / 10.12 秒**（两次几乎一模一样），而关掉加速时是 12.14 秒。

> 这个值原本没有注释说明为什么设，属于早期 bring-up 时留下的防御性写法。
> 去掉后自检的 proot 全部项目仍然 PASS，proot 自己也报
> `built-in accelerators: process_vm = yes, seccomp_filter = yes`。
> 万一将来某个机型不允许 seccomp，proot 会起不来，自检的
> TEST 4 / TEST 5 会**立刻**抓到 —— 不会变成"悄悄变慢"。

### ② 麦克风：把"到底卡在哪"钉死了

B 站有位用户反馈"加载了本地语音识别插件，但 App 不申请麦克风权限"。
**申请这一步 0.1.15 已经做了**（见下），这一版把剩下那半截查清楚了。

新增诊断接口 **`phone mictest`**：在 App 进程里直接用原生 `AudioRecord` 开一次麦。

实测结果（这台 vivo / Android 16）：

| 路径 | 结果 |
|---|---|
| 原生 `AudioRecord`（16 kHz / 44.1 kHz） | ✅ **初始化成功，能读到采样** |
| WebView `getUserMedia({audio:true})` | ❌ `NotReadableError: Could not start audio source` |

也就是说：**权限没问题、App 也能开麦，卡的是 WebView/Chromium 那一层** ——
而且从日志看，Chromium **连设备都没去碰**（全程没有任何 `AudioRecord`/`AudioFlinger`

换台手机跑一下就知道是不是这台机器的厂商策略问题。

### ④ 输入法：打完字**自动切回**了

之前为了让微信这类拦截注入的应用能打进字，App 内置了一个没有键盘的输入法
（「DSH 输入」），`phone text` 会临时把系统默认输入法切过去。
问题是**切完就留在那儿**，得靠 agent 记得执行 `phone ime restore`。
实测这不可靠 —— 一忙就忘，用户拿回手机发现自己的键盘没了。

现在打完字 **5 秒后自动切回**用户原来的输入法：

- 每次 `phone text` 都会把自动切回的计时**往后推**，
  所以连着填几个输入框不会来回切（那会让输入框反复失焦）；
- 两次打字间隔超过 5 秒才会切回去，下一次 `phone text` 会再自动切过来；
- **只在"当前默认输入法还是我们"时才还原** ——
  如果这中间用户自己把输入法换掉了，就不去抢，免得"用户刚选好又被改回去"；
- 手动 `phone ime restore` 仍然可用（会取消待执行的自动还原），但一般不需要了。

> 判定依据是**当前状态**，不是"这次走的哪条路" —— 这一点是实测踩出来的：
> `phone text` 先试无障碍，**成功就不走输入法那条路**，
> 可这时我们的输入法可能还留在系统里（上一次切换留下的），
> 于是"打字成功了"和"键盘还是我们的"同时成立，却没人去还原它，
> 用户的键盘就一直回不来。
> 现在只要"默认输入法是我们"就一定安排自动切回，
> **哪怕这次打字失败也一样** —— 失败恰恰是最容易把用户卡住的情况。

实测（QQ 搜索框，没有 Shizuku 因而切换要重新聚焦）：

| 步骤 | 默认输入法 |
|---|---|
| 起始 | `com.sohu.inputmethod.sogou.vivo/.SogouIME`（用户自己的） |
| `phone text` 后（这次提交失败） | `com.dsh.tdsh/…DshImeService`，桥状态显示"将在 5 秒后自动切回" |
| 再等 8 秒 | `com.sohu.inputmethod.sogou.vivo/.SogouIME` ✅ 自己回来了 |

`AGENTS.md` 里那条"★ 别忘了还原输入法"的硬性要求也随之删掉了 ——
这件事现在由 App 自己保证，不该再指望 agent 记得。

**现象**：点聊天里文件卡片的「打开 / 在侧边栏预览」，右侧栏确实弹出预览，
但里面看不到图 —— 用户原话是"有弹窗但是看不见"。

**根因**（实测出来的一手数据）：DSH 的文档预览是给**桌面**设计的，
图片按**原始尺寸**渲染，不做任何缩放：

```css
.JFRUHG_frame { width: max-content; min-width: 100%; padding: 8px }
.JFRUHG_image { width: auto; max-width: none; max-height: none; margin: auto }
```

于是 1080×2376 的截图在 360px 宽的面板里仍然是 **1080px 宽**：
实测 `img` 盒 `[8, -1177, 1080, 2376]`，而滚动容器 `scrollWidth=1096` vs
`clientWidth=352` —— 横向溢出三倍，只露一个角，还能左右拖。

**修法**：给预览的图片框加"缩到能看全"（宽度撑满、但不放大小图；高度按比例；
纵向仍可滚，长截图照样能往下看）：

```css
[data-sidebar-right-panel] [data-image-preview]{width:100%;min-width:0;height:auto;min-height:0}
[data-sidebar-right-panel] [data-image-preview]>img{width:auto;max-width:100%;height:auto;max-height:none}
```

**实测修后**：`img` 336×739、`scrollWidth 352 = clientWidth 352`，横向不再溢出。

> 定位用 `data-image-preview` / `data-sidebar-right-panel` 两个**稳定属性**，
> 不依赖 CSS Module 的哈希类名；也不限定窄屏 —— 平板的右侧栏一样窄，同样需要缩。

### ② 「打开方式」：以前必然失败，现在弹出系统选择器

**现象**：点文件引用或预览工具栏的「打开方式」，报
**「此主机没有可用的桌面，无法打开文件或文件夹」**。

**根因有两层**：
1. DSH 的 open-in-app 是**服务端**行为 —— 网页 POST `/open-in-app/open`，
   由**运行 dsh 的那台主机**去拉起桌面程序。手机上的"主机"就是 proot 容器，
   里面没有桌面环境，所以这个按钮在安卓上永远不可能成功。
2. 更早一层：它的交互是**两步** —— 先 `GET /open-in-app/apps` 拿"可用的桌面程序"
   列表，用户选一个才会 POST。而手机上那个列表**是空的**，
   于是菜单里一个选项都没有，点击根本走不到 launch()。

**修法**：注入脚本在**点击**这一层就接管两类按钮，直接走 App 的 JS 桥：

| 入口 | 定位方式 |
|---|---|
| 正文里的文件引用 | `button[aria-label^="在默认程序中打开 "]`，路径在同名 `title` |
| 预览工具栏的「打开方式」 | `[data-sidebar-right-panel] button[aria-label="打开方式"]`，路径在面板头部的 `[class*="_path"][title]` |

App 侧 `DshAndroid.openPath(path)` → 换成 `content://`
（targetSdk 28 直接传 `file://` 会抛 `FileUriExposedException`，必须用 FileProvider）
→ `ACTION_VIEW` + `createChooser("选择打开方式")`。
路径两种都认：手机存储的 `/sdcard/...`，以及容器内的 `/root/...`
（后者会映射回 App 私有目录里的 rootfs）。

另外还拦了一层 `window.fetch`（凡是发往 `/open-in-app/open` 的请求都改走安卓，
并回一个假的 200），作为兜底 —— DSH 以后再加新入口也自动覆盖。

**实测**：两个入口都能拉起系统选择器，窗口列表里出现
`com.android.intentresolver`，标题就是「选择打开方式」。

### ③ 白名单例外：agent 现在能点那个「选择打开方式」

**现象**：用户让 agent 操控学习通打开文件时，安卓会弹出**全屏**的
「选择打开方式」。agent 连看都看不到它，更别说点。

**根因**：那个弹窗（实测 `com.android.intentresolver`，窗口 `(0,0,1080,2376)`、
面积最大、`TYPE_APPLICATION`）**不属于任何白名单应用**，
前台判定拿到的就是它 → 白名单直接拒绝（`ERROR 500 ... 不在白名单里，已拒绝`）。
而且它全屏时会**盖掉底下应用的所有窗口** —— 所以"看看底下是谁"这招没用，
只能靠历史记录。

**修法**：三个条件**同时**成立才放行：

1. 当前前台是**选择器**（`com.android.intentresolver` / `android` / 包名含 resolver、chooser）；
2. **上一个**前台是白名单应用，且在 15 秒内（即"这弹窗是刚被白名单应用拉起来的"）；
3. 白名单非空。

边界没有实质放宽：**刻意不包含 systemui**（通知栏里能直接点权限开关），
普通第三方应用、系统设置、权限弹窗也都不在此列。

**实测**：

| 场景 | 结果 |
|---|---|
| 文件管理器（白名单）在前台 → 拉起选择器 → `/ui` | 返回完整控件树（原来是 `ERROR 500` 拒绝） |
| 同上，`/click text=微信` | `OK 已点击「微信」` |
| vivo文档（真实处理器、非选择器）在前台 | 仍然拒绝 ✓ 边界没漏 |

### ④ 麦克风：只声明，按需申请

- 清单里加 `RECORD_AUDIO`。**安装时不会授予任何东西** ——
  Android 6+ 的危险权限本来就必须运行时申请。
- WebView 侧补全 `onPermissionRequest`：网页要麦克风时先要系统权限，
  拿到再 `grant` 给网页（**只放行本机回环来源**，外部站点一律拒）。
  这个回调不实现的话，网页的音频捕获会被**静默拒绝**，用户什么都看不到。
- App 里加了「手机控制 → 麦克风权限」入口（已授予时跳系统应用详情页，方便关掉）。

**实测**（debug 版，`RECORD_AUDIO` 先 `pm revoke` 到未授予）：

| 步骤 | 证据 |
|---|---|
| 网页请求麦克风 → App 收到 | `onPermissionRequest origin=http://127.0.0.1:3080/ resources=[AUDIO_CAPTURE] RECORD_AUDIO=false` |
| App 转去要系统权限 | 同一次请求后紧跟一条 `RECORD_AUDIO=true` —— 中间那 3.5 秒就是系统授权框（本人点了允许） |
| 授权后网页拿到麦克风 | 后续请求直接 `grant` |

也就是说：**装完不会自动有麦克风；要用的时候才弹框问，用户同意后网页才用得上**，
正是想要的行为。

> ⚠️ **如实记一笔**：真正**采集音频**目前在这台机器上仍然失败，
> `getUserMedia` 报 `NotReadableError: Could not start audio source`。
> 已经排除的可能：权限没给（`granted=true`）、缺用户手势（用真实触摸点按钮一样失败）、
> AppOps 的 foreground 限制（显式设成 `allow` 也一样）、麦克风被别的应用占用（`dumpsys audio` 里没有）、
> 授权前进程缓存（重启 App 后一样）。
> 看起来卡在厂商音频策略那一层，**本版没有解决**。
> 权限链路的兼容性已经就位，等以后有语音插件时再继续查。

### ⑤ 新增诊断接口 `phone windows`

排查上面那些"看不见的系统弹窗"时，最缺的就是"现在到底有哪些窗口"。
新增 `phone windows`：列出每个窗口的包名 / 类型 / 区域 / 面积 / 根节点是否可读 / 类名 / 标题。

它**刻意不套白名单** —— 它只输出窗口元信息（不含任何控件文本），
而"白名单把系统弹窗误判成前台应用"这种故障，恰恰只有在被拒的那一刻看窗口列表才能定位。

## v0.1.14

这一版只改一件事：**侧边栏的会话条目改成「两次点击」**，
让每条会话右侧的「归档 / 重命名 / 分叉」终于点得到。

### 问题：想归档，就得先被迫切走一次会话

根因在 DSH 的 DOM 结构里 —— 「…」是**嵌在整行里面**的：

```
<div role="treeitem" onClick={onOpen}>        ← 整行都在"进会话"
  <span slot/><span title/><span time>3小时</span>
  <span rowActions><button>…</button></span>   ← 「…」在行内部
</div>
```

而 `rowActions` 的原生样式是 `display:none`，只有 `:hover` 或菜单已打开时
才 `display:inline-flex`，同时把右边的相对时间藏掉。

手机上就出现了死结：`touchstart` 那一刻浏览器才把 `:hover` 打到行上、「…」这时才出现，
**但 click 的落点在 touchstart 就已经定成了「行」**。
于是"让「…」出现"和"点「…」"永远是同一次点击 —— 用户想归档，就只能先被迫切走一次会话。

> 排查时踩的坑：一开始用 `Input.dispatchMouseEvent` 复现，怎么都复现不出来 ——
> 鼠标事件会先 `mouseMoved` 把 `:hover` 打上，click 的落点直接就落在「…」上了。
> **这个 bug 只在触摸下成立**，所以新增了 `tools/touch.mjs`，用
> `Input.dispatchTouchEvent` 派发真实触摸事件来验证。

### 改法

| 操作 | 行为 |
|---|---|
| 第 1 次点会话行 | 只把这一行的「…」亮出来，**不切换** |
| 第 2 次点同一行 | 正常切换会话（抽屉照旧自动收起） |
| 点「…」那一小块 | 只开菜单，**永远不切换** |

实现是在 `document` **捕获阶段**截住 click：命中会话行、且是"第一次"时，
给行打上 `data-dsh-armed` 并 `stopPropagation()`。
React 的事件委托挂在根容器上，所以这次 click 根本到不了 React，行的 `onOpen` 不会被调用。
（`stopPropagation` 拦不住**同一个节点**上的其它监听器，所以"点会话就收起抽屉"
那个监听器仍然看得到 `__dshConsumed` 标记，据此跳过收起 —— 两个监听器的
注册顺序有依赖，代码里已写明不能调换。）

样式上不依赖 hover 的粘滞行为：`data-dsh-armed` 那一行由 CSS **保证**
「…」可见、相对时间隐藏、行底色照亮，跟原生 hover 态长得一样。

**只对会话行生效**，判定条件是 `[class*="sidebarCol"] [role="treeitem"]`
**且没有 `aria-expanded`**。工作区行带 `aria-expanded`；
「新建会话」「设置」「鲸鱼按钮」压根不在 `treeitem` 里 ——
它们全部保持"单击即生效"。

### 实测（真机触摸事件，逐条确认）

| 操作 | 结果 |
|---|---|
| 点会话行（第 1 次） | 该行亮起、「…」出现、相对时间隐藏；**当前会话不变** |
| 再点同一行 | 切换会话 + 抽屉收起 |
| 点「…」 | 弹出「重命名 / 分叉会话 / 归档会话」；**当前会话不变**、抽屉不收 |
| 菜单开着时点别的行 | 菜单关闭、只亮出新行，不切换 |
| 点鲸鱼按钮 | 一次点击拉开抽屉 |
| 点「设置」 | 一次点击打开设置 |
| 点工作区行 root | 一次点击照常展开/折叠，不会被 arm |
| 收起抽屉再打开 | 上次亮着的行已经收回 |

## v0.1.13

这一版解决的是"**agent 到底能不能真的操作手机**"这件事。
之前它只能读控件树，而微信这类应用恰好把控件树屏蔽了；也不能稳定往里打字。
现在补齐了三块能力，并把手机控制做成了可扩展的插件体系。

### ① 让 agent "看得见" —— 截图能力

**根因是实测出来的**：微信对无障碍和 `uiautomator` **两条路都返回空树**
（只有 407 字节、1 个节点、`bounds=[0,0][0,0]`），但它**没有设置 `FLAG_SECURE`** ——
屏幕像素是完整可截的。所以读取这类应用只有一条路：**截图**。

两条后端自动选用：

| | 无障碍 `takeScreenshot` | 录屏 `MediaProjection` |
|---|---|---|
| 额外授权 | **不需要**（无障碍开着就行） | 要弹一次"录屏"确认 |
| 无障碍被关掉时 | 失效 | **照样能用** |

配上支持图片输入的模型（V4.1 Flash 就支持），截图经 `read_image` 进入模型视野，
agent 就能"看到"微信里的聊天列表、未读角标。

> 踩到的坑：Android 15/16 的录屏授权框**默认选中的是「共享一个应用」**，
> 不改成「共享整个屏幕」就只能截那一个应用。现在授权前会先提示。

**截图受白名单限制** —— 屏幕上有聊天记录、验证码，比点击更敏感。
前台应用不在白名单里时一律拒绝，跟读界面同一条边界。

### ② 让 agent "打得进字" —— 内置输入法

微信**拦截**两种常见注入方式，实测都进不去：

| 方式 | 微信里的结果 |
|---|---|
| 无障碍 `ACTION_SET_TEXT` | ❌ 被忽略 |
| shell `input text` | ❌ 同样进不去 |

但**输入法是系统认可的合法输入通道**，微信没法拦（否则真实用户的输入法也会被挡）。
`phone text` 现在会自动先试无障碍、失败就切到内置输入法。

**端到端实测**：注入后微信输入框里出现文字，而且**微信把「发送」按钮显示出来了**
—— 说明它把这段文字当成了合法输入。

> 关键技术点：只写 `Settings.Secure.DEFAULT_INPUT_METHOD` **不会让系统重新绑定输入法**，
> 服务起不来、`commitText` 无处可发。必须走官方的 `ime set` 命令
> （和桌面端 ADBKeyboard 的做法一致）。这正是"光改设置"失败的原因。

**安全兜底**：输入法界面上有「切回我的输入法」按钮，
AGENTS.md 里也把 `phone ime restore` 写成硬性要求 ——
否则用户会困在一个**没有键盘**的输入法里，连字都打不出来。

### ③ 手机能力插件化（随 APK 自带、自动安装）

`phone` 能力从"一个 CLI + 说明书"升级成**真正的 DSH 插件 bundle**，
随 APK 附带、首次启动自动装进 profile：

```
phone_status  phone_screenshot  phone_ui      phone_tap     phone_click
phone_swipe   phone_text        phone_key     phone_open    phone_ime
```

好处：这些工具直接出现在模型的工具列表里，带参数 schema、带错误说明，
不再需要 agent 先读 AGENTS.md 才知道有这么个东西。

> 插件会**自检并写一份结果**（`/sdcard/.dsh-phone/plugin-loaded.txt`），
> 而不是靠"dsh 没崩"来推断它生效了 ——
> 本项目在"加载了 ≠ 使用了"上栽过一次（垫片注入漏变量那次），不想再假设。
> 实测：`tools=10 registered=10 failed=[]`。

> 为了让插件市场能装**任意** npm 插件，容器里补装了 pnpm
> （`dsh plugin add` 内部要用它）。我们自己的插件零依赖，所以是离线解包的，
> 不依赖 pnpm。

### ④ 修复：安卓系统应用的工具栏"看不到、也点不动"

**现象**：agent 能读到系统「设置」的列表，却**看不到也用不了最上面那一排**
（标题、搜索框）。而人手动打开时那排明明就在。

**实测对比**：

| | 顶部工具栏 |
|---|---|
| `uiautomator` | `y=212 "设置"`、`y=373 "搜索设置项"` |
| 修之前我们的 `phone ui` | **第一条从 y=522 开始 —— 上面整排不存在** |

**原因**：系统应用把工具栏放在**独立窗口**里，而我们一直只读
`getRootInActiveWindow()`（当前**活动窗口**的根节点）。

修法分三处，缺一不可：

1. 开 `flagRetrieveInteractiveWindows`，用 `getWindows()` 逐个窗口渲染合并；
2. 前台判断改成**按屏幕面积取窗口** —— 原先依赖 `isFocused()`/`isActive()`，
   而 vivo 上 systemui 的浮层也会被标成 focused，导致前台被判成
   `com.android.systemui`，**所有操作被白名单拒掉，看起来却像"白名单配错了"**；
3. `ACTION_CLICK` 对**非活动窗口**的节点一律返回 false，
   所以加了**手势点击退路**（手势走输入系统，与窗口归属无关）。

**实测**：`phone ui` 能看到 `[42] ViewGroup "设置"` 和
`[44] LinearLayout "搜索设置项" (60,354,1019,450) 可点`；
`phone click "搜索设置项"` 成功，**截图确认设置搜索页真的打开了**。

> ⚠️ 顺带修掉一个**自己引入的卡死源**：`getWindows()` / `getRoot()` 都是同步 IPC，
> 我一开始把它们直接放在请求线程上跑，结果**整个控制桥卡死**。
> 加了 800ms 有界等待 + 1 秒缓存后，连续 3 次 `/ui` 都是 82~119 ms。

### ⑤ 插件市场

**DSH 设置 → 🧩 插件市场（本机）**：搜索 npm 上带 `dsh-plugin` 标签的插件、一键安装。

- 搜索直接问 npm registry（这正是 DSH 官方的插件发现机制），当前有 **6270+** 个包；
- 已装的显示 **✅已装** 并提供卸载；
- 装完提示重启 DSH 生效；
- 安装前**强制弹确认框**，明说"插件是第三方代码，装上会在你手机里运行"——
  这个信任判断不替用户做。

实测：`op=search` / `op=add`（真实装上 `dshmarket`，pnpm 5 秒完成）/ `op=remove` 全部通过。

### 界面调整

- **设置页的本机入口改成原生观感，去掉 emoji。**

  之前这四个入口**永远是高亮态、颜色和原生项不一致**。根因很具体：
  注入时用 `navList.querySelector('button')` 当模板 —— 那是**第一个**按钮，
  而它正是当前选中的那一项，className 里带着 `VOzbGW_active`。
  四个入口全都继承了这个"选中"样式（实测 `bg=rgb(67,69,74)`，
  而未选中的原生项是透明的）。

  现在改为**取一个未选中的原生按钮当模板**（拿不到就把 `active` 那一段剥掉），
  并去掉标签里的 emoji。实测四个入口的 class、背景、圆角、高度与原生未选中项完全一致：

  ```
  [1] 模型              cls="VOzbGW_navCell"  bg=rgba(0,0,0,0)
  [4] API Key（本机）    cls="VOzbGW_navCell"  bg=rgba(0,0,0,0)
  [7] 插件市场（本机）   cls="VOzbGW_navCell"  bg=rgba(0,0,0,0)
  ```

- **点本机入口不再"进去转一圈、退出掉回原生设置分类"。**

  因为这些入口不是 DSH 自己的分类，点它们不会改变弹窗的"当前分类"。
  本机页面抢走前台再交还时，弹窗可能已经落到某个原生分类的内容页上。

  修法：点这些入口时**记住"待返回"**，从本机页面回来（`visibilitychange`

### Shizuku 那条路真机验证通过（上一版遗留的"未验证"）

上一版标注了"Shizuku 的 UserService 执行路径尚未在有 Shizuku 的真机上验证过"。
这一版把它补齐了，**端到端跑通**：

1. 先用 `pm revoke` 把 `WRITE_SECURE_SETTINGS` 拿掉，制造"未授权"状态；
2. 在 App 里点「⚡ 用 Shizuku 授权」→ Shizuku 弹出授权窗 → 允许；
3. App 通过 `bindUserService` 把 `ShellUserService` 以 shell 身份拉起来，执行
   `pm grant com.dsh.tdsh android.permission.WRITE_SECURE_SETTINGS`；
4. `dumpsys package` 确认 **`granted=true`** —— **全程没有用电脑**。

顺带验证：授权后自愈功能恢复正常，连续 3 次清零都在约 350 ms 内补回。

### 修掉的三个真实缺陷（都是"静默失败"型）

1. **读到了上一位用户留下的旧文件。**
   `uiautomator dump` 失败时文件根本不会更新，而 `cat` 读到的还是**上一次**的旧 XML。
   旧 XML 里当然有 `<hierarchy>`，于是解析出 0 个节点，界面报"界面树是空的"，
   看起来像"目标应用屏蔽了 uiautomator" —— 实际上命令压根没跑成。
   **修法：dump 前先 `rm -f`**，让"文件不存在"把失败暴露出来。

2. **XML 声明前面多了一个换行，解析器直接罢工。**
   `echo '---XML---'` 天生带一个换行，于是 `<?xml ... ?>` 不再是文档的第一个字符。
   XML 规范要求声明必须在最开头，KXmlParser 抛
   `Unexpected token @2:1`，一个节点都解析不出来 —— 又一次伪装成"应用屏蔽了 uiautomator"。
   **修法：从 `<?xml` / `<hierarchy` 处切开再解析。**

3. **前台包名判断在弹出窗口时会判错。**
   一开始只用 `dumpsys window | grep mCurrentFocus`。目标应用弹出 `PopupWindow` 时，
   焦点窗口变成 `Window{com.chaoxing.mobile: parentWindow@... u0 PopupWindow:...}` ——
   这种形式里包名后面**没有斜杠**，正则匹配不到，反而匹配到列表里另一条属于我们自己 App
   的记录，于是**一次合法操作被白名单拒了**。
   **修法：首选 `topResumedActivity`**（指向正在 resume 的 Activity，不因弹窗/输入法漂移），
   `mCurrentFocus` 降级为退路，并校验结果像不像包名（含点、且全小写）。

> 三个缺陷有一个共同点：**都表现为"取不到界面"**，而真实原因分别是旧文件、换行、正则。
> 这正是为什么这一版把 `ShellControl` 的错误路径全部改成"把现场信息原样带出来"，
> 而不是返回一句笼统的失败。这个项目已经在"静默失败"上栽过好几次了。

### 说明：WeChat / QQ 读不出来

实测微信的界面树对 `uiautomator` 是**空的**（407 字节，根节点 `bounds=[0,0][0,0]`），
换成系统设置立刻是 35 KB 的完整树；而**无障碍后端读微信同样是空的**。
也就是说微信自己屏蔽了这两条读取路径，不是本 App 的实现问题。
需要在微信/QQ 上做自动化的话，这两条路目前都不通。

## v0.1.10

### 无障碍权限不再被厂商偷偷关掉（「无障碍守护」）

**现象**：vivo / iQOO 上，QQ、微信一切到前台，系统的无障碍总开关就被自动置 0，
DSH 的手机控制能力随机失效，只能反复手动去设置里重开。这是厂商的反诈策略。

**它是怎么被修好的**

要自动把开关写回去，需要 `WRITE_SECURE_SETTINGS`。这个权限的 protectionLevel 是
`signature|privileged|development` —— 普通安装拿不到，但**带 `development` 标志的权限
可以用 `pm grant` 单独授予**：

```
adb shell pm grant com.dsh.tdsh android.permission.WRITE_SECURE_SETTINGS
```

关键在于**授权结果是持久化的**（写进 packages.xml，重启手机、覆盖更新 App 都不会掉），
所以只需要做一次。这正是"懒人版"能成立的形态：一次动作，之后 App 自己维护自己。

拿到之后，App 内置的看门狗会在开关被关掉时把它写回去：

- **事件驱动**：无障碍服务被解绑的瞬间就有回调，立刻处理（这是厂商杀权限时最快的信号）；
- **轮询兜底**：每 3 秒读一次设置，覆盖"只改设置不解绑"的 ROM；
- **只追加自己**：名单里别人开的无障碍服务一概不动 —— 替用户复活他可能故意关掉的服务是越权；
- **可关**：设置页有明确的「无障碍自动守护」开关，关掉后本 App 不再碰无障碍设置，
  否则用户去系统里关权限、3 秒后被默默开回来，那就是流氓行为；
- **退避**：60 秒内反复被改掉 10 次以上就暂停 60 秒，不和 ROM 死磕耗电。

**实测（在真机上，用 adb 模拟厂商把开关清零）**

| 项目 | 结果 |
|---|---|
| 连续 5 次清零 | 5/5 自动恢复 |
| 恢复耗时 | 约 **350 毫秒**（含 adb 往返开销） |
| App 在后台时 | 照样恢复（守护跑在前台服务里） |
| 计数持久化 | 跨覆盖安装保留（6 → 10） |

> 修的过程中发现一个真实的延迟缺陷：最初 `nudge()` 只是置了个标志位，
> 而循环还在 `Thread.sleep(3000)` 里 —— 所谓"立刻检查"其实是"等这次休眠睡完"，
> 实测最坏要 4 秒才补回来。改成 `wait/notify` 唤醒后降到 350 毫秒。

### 接入 Shizuku：让没有电脑的用户也能完成那次授权

上面那条 `pm grant` 需要有电脑。没有电脑的用户现在可以走 Shizuku ——
它以 shell（uid 2000）身份替我们跑这条命令。设置页 →「📱 手机控制」→「⚡ 用 Shizuku 授权」。

- 依赖 `dev.rikka.shizuku:api` + `provider`（13.1.5），manifest 里注册 `ShizukuProvider`；
- 执行命令走官方推荐的 **UserService**：我们的 `ShellUserService` 被 Shizuku 以 shell 身份
  在独立进程里拉起来 —— 因为 Shizuku API 13.1.5 里 `Shizuku.newProcess()` 已经是 **private**
  （API 14 计划删除），客户端根本调不到；
- 没装 Shizuku 的手机上，整个 `ShizukuBridge` 静默降级：按钮照常可点，
  弹出的是"去哪装、怎么启动"的说明，不会崩溃、不会报错。

**关于「APK 自带 Shizuku 最高权限」** —— 做不到，而且不是实现问题。
Shizuku 的权限来自 ADB 或 root，是**从应用外面拿进来的**；官方开发文档明确要求
"引导用户先安装 Shizuku 或 Sui"。如果 APK 能给自己发这个权限，那它就是个通用提权漏洞。
我们能做的是把这一步压到最省事：装一次 Shizuku、点一下允许，之后永久有效。

> ⚠️ 诚实标注：Shizuku 那条路径（UserService 执行命令）**尚未在有 Shizuku 的真机上验证过**，

## v0.1.9

### 修复：平板/老 WebView 上"进了界面却用不了"（未连接、工作区列表空转）

有平板用户能打开界面，但工作区一直转圈、连不上，报
`AbortSignal.any is not a function`。

**根因**：不是一个平板专属的 bug，而是一个**所有人都中招、只有老机器才看得出来**的问题。

`AbortSignal.any` 要 Chrome 116+ 才有（`structuredClone` 98+、`Iterator` 122+）。
DSH 的 Web 客户端用这些新 API 兜住了"取消请求"这条公共路径，
于是 **WebView 版本低于 116 的机器**上，凡是要发请求的地方都会卡死：
工作区列表永远停在"正在加载工作区…"，连接状态永远"未连接"。

同一个根因，两个看起来毫不相干的症状。

**这次修掉了两层问题：**

1. **垫片（`webview-shim.js`）以前根本没被注入。**

   项目里早就写好了兼容垫片，`MainActivity` 也把它读进了变量，
   但注入语句在一次改动中被写成只注入调试用的删除器，
   `webCompatShim` 被漏掉了 —— 也就是说**这个文件从来没进过页面**，
   老机器照旧报错。

   现在两个变量会拼在一起注入；正式构建里删除器是空串，
   等价于"只注入垫片"。

2. **补齐了 `AbortSignal.any` / `AbortSignal.timeout` /
   `AbortSignal.prototype.throwIfAborted` / `structuredClone`。**

   垫片一次性覆盖到 Chrome 116 这一档，凡是 WebView ≥ 98
   （Android 7 以上基本都满足）的机器都能正常收发请求。

**验证方式**（在最新版 WebView 上复现老机器的故障）：

- 先用删除器把 `AbortSignal.any` / `structuredClone` 等删掉 → 复现成功：
  工作区列表停在"正在加载工作区…"，只有"添加工作区…"一项。
- 再让垫片在**同一个页面**上把删掉的 API 补回来 → 工作区 `root` 立刻出现，
  模式、权限、模型选择器全部正常，连接状态正常。

同时确认了垫片的**注入时机**够早：删除器能生效，说明注入发生在
DSH 页面脚本之前，垫片同理。

### 平板不再被"跳过"

窄屏补丁里有一句 `if (!narrow) return;`（`narrow` = 屏宽 < 700px），
本意是"平板不需要手机那套布局补丁"，实际效果却是**平板拿到了一个完全没打过补丁的 DSH**。

现在把与宽度无关的三件事拆出来无条件执行：

- **回车 = 换行**（发送只靠右下角按钮）—— 平板接外接键盘时同样适用
- **「添加工作区」对话框里的手机目录快捷入口**（手机存储 / 下载 / 相册…）
- **落地页右上角那个多余的侧边栏按钮**不再显示

仍然只在窄屏生效的：抽屉式侧边栏、设置页"列表 → 详情"单栏切换
（平板本来就是常驻侧边栏 + 双栏设置，套用会弄坏布局）。

**结论：不需要单独做一个平板安装包。** 平板的问题（老 WebView API 缺失）
跟屏幕宽度无关，同一个 APK 在手机和平板上都能用；
真正跟宽度有关的差异已经在上面按条件分开了。
少一个包就少一半的维护量和一半的"用户装错包"。

### 修复：容器装好了、但 `dsh web` 起不来（一直"初始化失败"）

**现象**：所有自检全部通过（容器、Node、DSH、存储都 ✅），
但最后卡在"等待 dsh web"，4 分钟后变成**初始化失败**，
而且屏幕上**看不到任何原因**。

**原因（三个叠加）**：

1. **端口被占用时 dsh 起不来，而且会无限重启。**
   `dsh --port 3080` 撞上已有进程就绑不上端口，进程立刻退出；
   监督循环每 5 秒重启一次，于是**永远拿不到 URL**。
   3080 是个很容易撞车的端口。
2. **dsh 的输出被丢掉了。** 原来那段代码**只看 URL、其余全部忽略** ——
   所以 dsh 为什么起不来，日志里一个字都没有，只能看到"超时"。
3. **失败原因被自己擦掉了。** `onProvisionFailed` 已经往日志区写了原因，
   但紧接着的收尾代码用 `setText(...)` **整段替换**了日志区，
   于是屏幕上只剩"初始化失败"四个字。

**修复**：

- **端口自动避让**：启动前先探一遍，3080 被占就依次试 3081…3090。
  实测验证：占住 3080 后，dsh 自动改用 **3081** 并正常加载。
- **保留 dsh 输出**：前 30 行 + 任何像报错的行都写进日志；
  最近 12 行会在失败时直接显示在屏幕上。URL 匹配也放宽了
  （不再死认 `127.0.0.1`，`localhost` / `0.0.0.0` 也能识别并归一化）。
- **失败时只追加、不替换**，原因不再被擦掉。
- **失败信息更具体**：带上服务状态、实际端口、dsh 最后输出。
- **快速识别"前台服务没起来"**：20 秒内发现服务没创建就直接报
  "系统可能拦截了后台服务"，不用白等 4 分钟。
- **回到前台时自动跟随地址变化**（容器在后台重启过、token/端口变了，
  WebView 还指着旧地址会连不上，现在会自动重新加载）。

## v0.1.6

### 修复：部分老手机打开就报 `Failed to load plugins`

**现象**：DSH 界面起不来，整页只有一行错误：

```
HARNESS
Failed to load plugins
failed to import loader entry 0873777a
(@deepseek-ai/dsh-client-ui-sidebar-documentpreview): Iterator is not defined
```

**原因**：DSH 的 Web 客户端用了一批较新的 JS 特性，手机自带的**系统 WebView 太旧**时，
插件在**加载阶段**就抛 `ReferenceError`。`Iterator` 是 Chrome 122+ 才有的全局对象，
而报错那段插件代码是：

```js
if (typeof Iterator.prototype.join !== "function")   // ← Iterator 不存在时这一行就抛错
    Iterator.prototype.join = function (s) { return [...this].join(s); };
```

它想"缺了就补"，却忘了 `Iterator` 这个全局本身可能不存在。

**修复**：内置一个**兼容垫片**（`app/src/main/assets/webview-shim.js`），
在页面脚本执行前补齐缺失的 API。全部是**幂等的能力检测** ——
现代 WebView 上补 0 项、零开销（实测 Android 16 / WebView 138 上 `applied: []`）。

补齐清单（括号内为最低 Chrome 版本）：

| 特性 | 最低版本 |
|---|---|
| `String.prototype.replaceAll` | 85 |
| `String.prototype.at` / `Array.prototype.at` | 92 |
| `Object.hasOwn` | 93 |
| `Array.prototype.findLast` / `findLastIndex` | 97 |
| `Array.prototype.toSorted` / `toReversed` / `toSpliced` / `with` | 110 |
| `String.prototype.isWellFormed` / `toWellFormed` | 111 |
| `Object.groupBy` / `Map.groupBy` | 117 |
| `Promise.withResolvers` | 119 |
| `Array.fromAsync` | 121 |
| **`Iterator`**（含 `Iterator.from` 与迭代器辅助方法） | **122** |
| `Set.prototype` 集合运算（union/intersection/…） | 122 |
| **`URL.parse`** | **126** |

**另外**：日志里会记录 `[WebView] Chrome/<版本> · 垫片补充: [...]`。
出问题时在 App 的「设置 → 复制日志」里可以一键复制发出来。

## v0.1.5

### 修复：新手机首次使用会永久卡在「正在重启容器内的 DSH…」

这是最严重的一个：**别人装好后一直停在那一句话上，怎么等都没用，只能卸载重装。**

四个原因叠加：

1. **容器里的命令没有任何超时。** 首次初始化要跑
   `npm install -g @deepseek-ai/dsh`（界面自己都提示可能 5-15 分钟），
   这条命令一旦因为网络 / 容器内 DNS 卡住，`waitFor()` 会永远等下去 ——
   整个初始化线程挂死，界面就停在最后一句话上。
2. **下载只有"单次读取 60 秒"超时**，没有总时长上限；
   而且进度只写进日志文件，普通用户看不到 —— "正在下载"和"卡死"在界面上长得一模一样。
3. **初始化没有顶层异常兜底**，而且可以重复启动
   （切后台再回来会起第二个线程，两个线程同时解压 / 装 npm）。
4. **首次启动会立刻弹出 API Key 对话框**，用户一点「保存并重启」，
   容器其实还没装好 —— 界面被切成"重启中"，4 分钟超时后又**没有任何恢复入口**。

**修复**：

- 所有耗时命令加 **超时 + 心跳**：npm 25 分钟总时长 / 5 分钟无输出即判卡死；
  其它容器命令 120 秒；下载加总时长上限与停滞检测，并**在界面上显示下载进度**。
- 初始化加**顶层兜底 + 防重入**：失败一定会变成"看得见的错误"，不再静默挂死。
- 顶部新增 **「重试」**（失败时出现；**长按 = 清空容器重新初始化**）。
- 状态栏显示**已耗时**（`初始化中 03:12 · 当前步骤`），一眼区分"在跑"和"卡死"。
- 容器没装好时**不再弹阻塞式对话框**；按钮变成「保存」并提示会在启动时自动生效。
- 服务侧修了重启竞态（重启后新 token 能被正确解析）。
- 服务发现"容器未安装完成"时，回到 App 会**自动补跑初始化**。
- 新增 **「复制日志」**（设置里），出问题可以把日志直接发出来。

### 其它

- 签名增加 v3 方案，提升安装兼容性（v0.1.4 的内容）。
- 修复点「设置」时先闪一下「通用设置」详情页（v0.1.3 引入的回归）。
